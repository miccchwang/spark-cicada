# 10 · 钉钉协作与续跑机制

> 解决用户第三轮提出的问题：**「钉钉回复无法直接启动下一轮工作」**。
> 版本 v1.0（2026-10-05）

---

## 1. 问题定义

原有做法：
```
我 → 钉钉单聊发「决策清单」→ 用户回复 → 我读取回复 → 继续
```
缺口：**用户回复后，没有任何东西自动触发我"继续"**。
用户必须回到对话里手动发一句「已回复」，我才会去读。
如果用户忘了发，工作就停在那里。

---

## 2. 三种续跑通道

| 通道 | 触发方式 | 适用 | 是否自动 |
|---|---|---|---|
| **A 定时轮询（推荐）** | 定时任务定期读用户钉钉单聊 | 需要决策等待时 | ✅ 全自动 |
| **B 卡片回调** | 钉钉交互卡片按钮 → 回调 Webhook | 交互式决策 | ✅ 全自动 |
| **C 手动戳一下** | 用户在对话里说「已回复」 | 兜底 | ❌ 手动 |

本项目**默认启用通道 A**，通道 B 作为 M4 里程碑的增强项。

---

## 3. 通道 A：定时轮询机制

### 3.1 工作方式

```
[我] 发出决策清单 + 在消息里附「回执编号 R-YYYYMMDD-N」
      ↓
[我] 登记一个「待决策」状态（写下：待决事项、回执编号、超时时间）
      ↓
[定时任务] 每 N 分钟读一次用户的钉钉单聊最新消息
      ↓
[定时任务] 发现带匹配回执编号 / 在超时窗口内的新回复
      ↓
[定时任务] 自动把回复解析成决策 → 落到 docs/06 → 继续下一轮工作
      ↓
[我] 把处理结果回发钉钉，闭环
```

### 3.2 回执编号协议

每条发给用户的决策请求，末尾必须带：

```
【回执编号】R-20261005-01
【待决】D12 / D13 / D14
【超时】2026-10-06 20:00（超时则按默认项继续，并标注"默认执行"）
```

- 用户在回复里**带上回执编号**（或直接回复该消息），轮询即可精准匹配。
- 同一条请求只处理一次，避免重复触发（用回执编号去重）。

### 3.3 轮询任务规范

| 项 | 值 |
|---|---|
| 频率 | 每小时检查（可调；有未决事项时可加密到 15 分钟） |
| 读取目标 | 用户本人钉钉单聊（open-dingtalk-id 固定） |
| 匹配规则 | 消息含回执编号 或 时间戳晚于请求发出时间 |
| 去重 | 已处理回执编号写入本地状态文件 |
| 超时策略 | 超时后按"推荐项/安全默认项"继续，并在钉钉标注 |
| 无新回复 | 静默退出，不打扰用户 |

### 3.4 状态文件

```
.workbuddy-ai/state/dingtalk-pending.json
{
  "pending": [
    {
      "receiptId": "R-20261005-01",
      "topics": ["D12", "D13", "D14"],
      "sentAt": "2026-10-05T20:10:00+08:00",
      "deadline": "2026-10-06T20:00:00+08:00",
      "defaultOnTimeout": "按推荐项执行",
      "status": "WAITING"
    }
  ],
  "processed": ["R-20261004-01"]
}
```

## 5. 通道 C：手动兜底

用户在对话里说「已回复」/「继续」时：
1. 我立即读钉钉单聊最新消息；
2. 解析决策 → 落文档 → 继续；
3. 回发钉钉确认。

> 这是当前**已可用**的通道，通道 A 是对它的自动化封装。

---

## 6. 消息发送规范（避免踩坑）

承袭此前经验（2026-10-06 现场实测校正）：

| 坑 | 规避 |
|---|---|
| 超长内容 + `--content "$(cat file)"` 导致超时/SIGTERM | **消息保持简短单行**；长文档只发"摘要 + 仓库路径" |
| 中文/特殊字符 | 用 UTF-8，避免 shell 转义问题 |
| 目标 | 用户本人单聊：`+dm --to "CN-Michael-黄基煜"` |
| 读回复 | `+chat-messages --user 011942663154-1575976441 --direction older`（★ `--direction older` 返回顺序是**新→旧**，数组第一个最新；漏掉该 flag 会得到 `count=0` 的空页，看着像「没有新消息」，实际是读反了方向） |
| ★ 非交互环境发送被拒 | 必须显式 `--yes`，否则 `confirmation_required`（code 3）。成功判据是 **`result.success == true`**，顶层 `success` 字段是 `null`，不要按它判 |
| ★ 长度硬约束并不绝对 | 实测 22 / 95 / 128 / 136 / 140 字符均送达成功；135/233/424 字符曾全部 SIGTERM。**保持精简即可，不必死守 100**；真失败时先缩短再发，不要原样重试 |
| ★ push 到 spark-cicada | `origin` 是 `git@github.com:...`，而 SSH agent 里未必有 sparkcicada 的 key ⇒ `Permission denied (publickey)`。**改用 `~/.ssh/config` 里的别名内联推送**：`git push git@github-sparkcicada:miccchwang/spark-cicada.git main`；连通自检 `ssh -T git@github-sparkcicada` → `Hi miccchwang/spark-cicada!` |

> **运行闸门纪律（血泪教训）**：轮询任务**永远无条件读回**单聊最近消息，
> **绝不**用 `pending[]` 是否非空当运行前提 —— `pending` 在用户回复后即被清空，
> 拿它当闸门会导致「用户一回复 → 下轮永远无事可做」的静默停摆。
> 唯一允许静默退出的条件：读回后确认**没有新的用户消息**。

## 7. 闭环示意

```
┌─────────────────────────────────────────────────────────────┐
│  我：产出决策清单 ──► 钉钉（带回执编号）──► 用户              │
│                                              │               │
│                                              ▼               │
│  定时任务：轮询用户钉钉单聊 ◄──────────── 用户回复            │
│       │                                                      │
│       ├─ 匹配回执编号 → 解析决策 → 落 docs/06 → 继续工作      │
│       ├─ 回发处理结果到钉钉（闭环）                           │
│       └─ 超时未回 → 按默认项继续 + 标注                       │
└─────────────────────────────────────────────────────────────┘
```
