# 03 · 算法 · 数据槽 · 规则 参考手册

> 本文是「算法与数据来源分离」原则（`01-开发文档.md` §5）的**落地字典**。
> 版本 v1.0（2026-10-05）· 状态：结构已定稿，具体值随接入进度填充。

---

## 1. 三者的正交关系

```
        算法 (Algorithm)              数据槽 (DataSlot)           规则 (Rule)
   ┌──────────────────────┐    ┌──────────────────────┐  ┌──────────────────┐
   │ 只回答：              │    │ 只回答：              │  │ 只回答：          │
   │ 「怎么算」            │    │ 「数据从哪来」         │  │ 「用什么口径/费率」│
   │  gp = rev - cogs      │    │  成本 ← 成本主数据     │  │  TK 佣金 = 10%    │
   └──────────┬───────────┘    └──────────┬───────────┘  └────────┬─────────┘
              │                            │                        │
              └────────────────────────────┼────────────────────────┘
                                           ▼
                                  预计算桶 (Bucket)
```

**为什么要拆开**：
- 换数据源（如成本从主表改为 API）→ 只改**数据槽**，算法不动
- 改口径（如佣金费率调整）→ 只改**规则**，算法不动
- 改算法（如毛利率改为考虑退货）→ 只改**算法**，数据源不动

## 2. 数据槽清单（DataSlot）

### 2.1 状态定义

| 状态 | 含义 | 覆盖率 |
|---|---|---|
| `AVAILABLE` | 数据完整可用 | ≥ `coverage_gate` |
| `PARTIAL` | 部分可用，但低于门限 | < `coverage_gate` |
| `MISSING` | 无权威来源 | 0 |

> **PARTIAL 与 MISSING 对算法同等对待**：均触发 `skip`（不补 0、不摊分）。

### 2.3 槽定义示例

```yaml
# slots/slot.cogs.yaml
id: slot.cogs
name: 成本额
source_kind: master_table
source_ref: cost_master.v2
key_strategy: barcode_then_sku          # 完整条码优先，无条码用品牌+精确归一化 SKU 名
coverage_gate: 0.80                     # 低于 80% 视为不可用
freshness: 7d
permission: L4
notes: |
  成本主数据按固定列位解析；表头变化须显式失败，不做模糊匹配。
  未命中保留空值（显示 —），禁止用 0 或均价替代。
```

> **★ `source_kind` 与 `source_ref` 的语义 —— 声明必须可解析，不能是装饰**
>
> | `source_kind` | 含义 | `source_ref` 要求 |
> |---|---|---|
> | `master_table` | 主数据表 | **必填**，指向具体主数据（如 `cost_master.v2`） |
> | `api` | 外部 API | **必填** |
> | `mcp` | MCP 工具 | **必填** |
> | `skill` | 技能 | **必填** |
> | `upload` | 人工上传 | **必填** |
> | `derived` | **派生槽**（由桶/事实表算出，非直接采集） | **可空**；一旦填写，必须是 **fact 表全称/简名** 或 **已物化的桶 ID**，否则是「幽灵引用」 |
>
> **允许值以 `sql/0005` 的 CHECK 约束为事实源**（`master_table` / `api` / `mcp` / `skill` /
> `derived` / `upload`）—— **不含 `db` / `file`**（`admin/plane.go` 的注释曾误列二者，
> 以迁移为准；闸门已断言「迁移允许集合 ⊆ `gate.SlotSourceKinds()`」防两侧漂移）。
>
> **占位符一律拒绝加载**：`todo` / `tbd` / `x` / `-` / `?` / `n/a` / `none` / `待定` / `无`
> 等（归一化大小写/空白/下划线后精确匹配）。反向有「不误伤」纪律：`x_api` / `xray.ads` /
> `tbd_report` / `todo_master` 是**合法** ref（不是占位符）。
>
> **为什么必须判定**：`source_kind` / `source_ref` 此前**被读、被存进 `registry_slot`，
> 却从未被任何断言消费** —— 唯一的校验是 `SourceKind == ""`。于是 `source_ref: x`、
> `source_kind: 想写什么写什么` 一律照过（**声明等于装饰**）。
> 派生槽的 `source_ref` 到底该指向 fact 表还是已物化桶，代码里根本没有答案。
> 闸门首日即抓到真缺陷：`slot.gross_profit` 的 `source_ref: pnl_sku_month` 指向一个
> **并不存在的桶**（唯一桶是 `pnl_month`）。
>
> **装载顺序**：`LoadRegistry`（槽）先于 `LoadBucketRegistry`（桶）—— 派生解析依赖桶，
> 故必须在桶装载后经 `slot.ValidateWithBuckets` **重校验**（`sparkd loadSpecs` 调用）。
> **派生的 `ref` 在桶到位前不做解析**（否则是一段静默放行窗口）；**未解析（nil resolver）
> = 不通过**（fail-closed）。
>
> 判定实现：`gate.CheckSlotSourceResolvable` / `IsPlaceholderRef` / `FactTables`
> + `slot.ResolveDerived` / `ValidateWithBuckets`。详见 `05-验收闸门.md` 的「G4 第六侧」收口。

> **★ `key_strategy` 的语义 —— 声明必须可解析，且跨槽必须一致**
>
> `key_strategy` 回答「**多条来源按什么键合并成一行**」。上表「匹配键」列
> 与 YAML 的 `key_strategy` 是**同一个事实的两种写法**，故：
>
> | `key_strategy` | 匹配键列写法 | 语义 |
> |---|---|---|
> | `direct` | `—` | 整行直达（主数据行即键，不做跨源合并） |
> | `store_sku` | `store+sku` | 店铺 + SKU（渠道流水与成本的默认对齐口径） |
> | `sku` | `sku` | 仅 SKU（库存/物流等以 SKU 为唯一粒度的来源） |
> | `spu` | `spu` | 仅 SPU（达人佣金/市场费用按 SPU 计提） |
> | `channel_day` | `channel+day` | 渠道 + 日期（广告花费按渠道逐日对齐） |
> | `shop_txn` | `shop+txn` | 店铺 + 交易号（平台费用按交易逐笔对齐） |
> | `date_pair` | `date+pair` | 日期 + 货币对（汇率按日、按货币对对齐） |
> | `barcode_then_sku` | `barcode→sku` | 完整条码精确匹配优先，无条码退到品牌+归一化 SKU 名（成本主数据专用） |
>
> **为什么必须判定**：`key_strategy` 此前**被读、被存进 `registry_slot`，
> 却从未被任何断言消费** —— 全链路只有解析/赋值/写库三类用法，**没有第四类**。
> 于是 16 个槽全声明了它，而 `store_sku` 与`随便写`行为完全等价。
> 后果不是「少一条断言」，而是**跨源对齐口径失去判据**：写错它桶照样算出来，
> 但合并后每一行都可能张冠李戴（A 店成本配到 B 店收入上），**全程零报错**。
> 静默的错数，比缺数危险得多。
>
> **★ 共用来源的槽，键口径必须一致**：若两个槽的 `source_kind` + `source_ref` 相同
> 却声明了不同键，则同一来源被按两种口径合并，结果必然对不上。
> 这是「逐条校验都过、合起来是错的」那类缺陷，**单元断言看不见**，
> 故单列一条跨槽判定（`gate.CheckKeyStrategyCohesion`）。
> 例外：`direct`（整行直达）与明细键**允许共存**于同一主表引用下 —— 读法不同不等于冲突。
>
> 判定实现：`gate.CheckKeyStrategyDeclared` / `ParseKeyStrategy` / `CheckKeyStrategyCohesion`
> + `slot.KeyStrategyDocs` → `Validate`（真实生产调用点）。
> 详见 `05-验收闸门.md` 的「G4 第七侧」收口。

> **★ `coverage_gate` 与 `freshness` 是两个不同的问题 —— 两个都必须有判定**
>
> | 字段 | 回答的问题 | 判定落点 |
> |---|---|---|
> | `coverage_gate` | 这一份数据**全不全** | 覆盖率低于门限 ⇒ 槽 `DEGRADED` ⇒ 依赖算法 `skip` |
> | `freshness` | 这一份数据**新不新**（距上次成功采集多久算过期） | 数据龄超过时效 ⇒ 槽 `DEGRADED` ⇒ 依赖算法 `skip` |
>
> **一份覆盖率 100% 但停在三个月前的快照，跑出来的 P&L 是旧的**，
> 而只看覆盖率这一维它是「完好的」—— 这正是 `freshness` 必须参与判活的原因。
>
> **格式**：`<正整数>` + 单位，单位 ∈ {`m` 分, `h` 时, `d` 天, `w` 周}（如 `30m` / `12h` / `1d` / `7d` / `2w`）。
> 自由文本（`daily` / `7天` / `1 day`）、小数（`1.5d`）、`0d` 一律**加载失败** ——
> 它们看似合理，但解析器拿不到时长，判定会退化成「不影响任何事」。
>
> **异常口径（fail-closed）**：**没有新鲜度读数 ⇒ 按过期处理**，不是按新鲜处理。
> 否则采集器整个挂掉这条通道，反而会让所有槽都判活 —— 失效方向恰好反了。
> 龄为负（时钟回拨 / 脏数据）同样按过期处理。
>
> 判定实现：`gate.CheckFreshnessDeclared`（声明层）+ `gate.ParseFreshness`（唯一解析权威）
> + `slot/coverage.go: CheckFreshness / Cases / Judge`（判活）。
> 详见 `05-验收闸门.md` 的「槽的采集时效闭环」（第十三个变种）。

## 3. 算法清单（Algorithm）

### 3.1 算法定义格式

```yaml
id: algo.<name>
name: 中文名
version: <int>
status: ACTIVE | PENDING         # 可选，缺省 ACTIVE（见下）
formula: <纯公式>
unit: THB | % | count
permission: L1..L4                # ★ 必须可解析且是 L1/L2/L3/L4 之一（G4 第八侧，见下）
depends_on_slots: [...]          # 数据槽依赖（G4 要求算法与数据源分离）
depends_on_algos: [...]          # 可选：算法依赖算法（链式，见下）
writes_bucket: <bucket_id>
missing_policy: skip | null | error
trace: true
```

#### ★ 密级（`permission`）的**可解析性**约定（2026-10-07 新增闸门 / G4 第八侧）

`slots/*.yaml` 与 `algorithms/*.yaml` 的 `permission` 必须是
**`L1` / `L2` / `L3` / `L4`** 之一（`docs/01 §13.3`：L1 公开 / L2 内部 / L3 敏感 / L4 核心），
并与 `sql/migrations/0002_slots_and_rules.sql` 的
`CHECK (permission IN ('L1','L2','L3','L4'))` **同源**。

- 允许大小写差异（`l4` → `L4`，笔误且无歧义）；
- **不允许别名**：`核心`、`高密`、`L4级`、`internal`、`L5` 一律**加载失败**。

> ★ **注意：密级不是沿依赖链单调的，本闸门也刻意不这么断。**
> 实测样例：`algo.cogs` 声明 `L4`，其原料之一 `slot.qty`（销量）声明 `L2` ——
> 「卖了多少件」属内部、而「每件成本多少钱」属核心，**低密级体量原料造出高密级成品
> 在业务上完全正当**；反向亦然（`algo.gp = revenue − cogs`，减法降低敏感度）。
> 若强行要求「算法密级 ≤ 原料槽密级」，只能靠抬高 `slot.qty` 或压低 `algo.cogs`
> 来满足，后者等于**把核心成本降级** —— 那是真正的安全回归。
> 故闸门只钉「档位已知 + 与 DB 词表同源」，**不钉它装不下的东西**。

#### ★ 公式自由变量的**值绑定**约定（2026-10-07 新增闸门）

`formula` 里的**自由变量必须能被绑定**，否则内核会**静默**取缺失
（`spark-compute` 的 `eval_formula` 对查不到的变量返回 `Scalar::Missing`，**不报错**），
配合 `missing_policy: skip` 就会让该列在**每条数据**上被跳过 —— 全空、零报错。

绑定来源有二，命名约定唯一：

| 来源 | YAML 键 | 变量名 | 例 |
|---|---|---|---|
| 数据槽 | `depends_on_slots` | `BareName(槽 ID)` | `slot.revenue` → `revenue` |
| 上游算法 | `depends_on_algos` 或桶 `produced_by` 中**排在本算法之前**的算法 | `BareName(算法 ID)` | `algo.gp` → `gp` |

> **反面教材（本闸门上线首日实测抓到）**：`algo.gp` 的公式曾写 `rev - cogs`，
> 而依赖槽是 `slot.revenue`（绑出的变量名是 `revenue`）⇒ `rev` 永远取不到值。
> 同类还有 `algo.gmp`（`rev == 0 ? null : gp / rev`）与
> `algo.net_contrib`（`cm2 - overhead_alloc`，两个变量在全仓**无任何定义**）。
> 前两者已修变量名；后者如实标为 `PENDING`（不臆造来源）。
> 静态校验见 `gate.CheckFormulaVariablesBound`，运行时折算见 `precomp.BuildRow`
> （两者共用同一条 `compute.BareName`）。

#### ★ `status: PENDING`（口径未定 / 实现待补）

某些算法的口径仍在决策中（如 `algo.net_contrib` 依赖的 `algo.cm2` /
`overhead_alloc`）。这类算法**如实标 `PENDING`**，其效果是：

* 绑定闸门**不要求**其自由变量可绑定（因为来源本就还没有）—— 但 `formula` 必须非空
  （否则「待补」是一个没有任何内容的空壳，无从判断待补什么）；
* **禁止**它出现在任何桶的 `produced_by` 里（`gate.CheckPendingAlgosNotProducing`）
  —— 一旦入桶，运行时它就是一条恒空的静默列；
* 待口径拍板、来源补齐后改回 `ACTIVE` 并重新入桶。

⇒ 「已知的未完成」由此成为一个**可被断言的状态**，而不是静默通过。

### 4.3 口径切换规则（承袭 KODP 实测结论）

| 口径 | 定义 | 影响 |
|---|---|---|
| **A 参考口径** | Seller Discount 计入营销费用 | 营销费用虚高，易误读为"费用失控" |
| **B Finance 口径** | Seller Discount 作 contra-revenue（收入抵减） | 揭示真实问题是"折扣压缩毛利" |

**KODP 实测（JupJup TH，2026-08/09）**：

| 指标 | 口径 A | 口径 B |
|---|---:|---:|
| 8 月净贡献 | -152,567.19 | **+123.17** |
| 9 月净贡献 | -2,945,788.22 | **-119,826.78** |

> **关键结论**：净收入两口径**完全相同**（折扣本就从 GMV 扣除），
> 只是从"费用侧"搬到"收入侧"展示。**口径切换会完全改变经营解读**，
> 所以规则层必须支持切换，且默认口径须经用户拍板（决策项 D10）。

## 5. 值输出保证流程

对每个请求字段执行（对应 `01-开发文档.md` §5.5）：

```
1. 取字段 → 找算法 (algo_id)
2. 收集 algo.depends_on_slots 中**每个槽**的状态
3. 判定：
   ├─ 全部 AVAILABLE 且覆盖率 ≥ 门限 → 执行公式 → 得值
   └─ 任一 NOT AVAILABLE → 值 = null + 标记 skipped + 记录 reason
4. 写入 AlgoTrace（field, algo_id, slots, skipped, reason）
5. 渲染层：null → 显示「待接入」/「—」
```

**三条铁律（CI 闸门断言）**：
1. 任何非空值必须有对应 `AlgoTrace` 且 `skipped=false`
2. 任何 `skipped=true` 的字段，契约值必须为 `null`
3. 不得出现 `0` 作为缺失占位（`0` 只能是真实计算结果）
