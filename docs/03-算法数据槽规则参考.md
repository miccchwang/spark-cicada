# 03 · 算法 · 数据槽 · 规则 参考手册

> 本文是「算法与数据来源分离」原则（`01-开发文档.md` §5）的**落地字典**。
> 版本 v1.0（2026-10-05）· 状态：结构已定稿，具体值随接入进度填充。

---

## 1. 三者的正交关系

```
        算法 (Algorithm)              数据槽 (DataSlot)           规则 (Rule)
   ┌──────────────────────┐    ┌──────────────────────┐  ┌──────────────────┐
   │ 只回答：              │    │ 只回答：              │  │ 只回答：          │
   │ 「怎么算」            │    │ 「数据从哪来」         │  │ 「用什么口径/费率」│
   │  gp = rev - cogs      │    │  成本 ← 成本主数据     │  │  TK 佣金 = 10%    │
   └──────────┬───────────┘    └──────────┬───────────┘  └────────┬─────────┘
              │                            │                        │
              └────────────────────────────┼────────────────────────┘
                                           ▼
                                  预计算桶 (Bucket)
```

**为什么要拆开**：
- 换数据源（如成本从主表改为 API）→ 只改**数据槽**，算法不动
- 改口径（如佣金费率调整）→ 只改**规则**，算法不动
- 改算法（如毛利率改为考虑退货）→ 只改**算法**，数据源不动

## 2. 数据槽清单（DataSlot）

### 2.1 状态定义

| 状态 | 含义 | 覆盖率 |
|---|---|---|
| `AVAILABLE` | 数据完整可用 | ≥ `coverage_gate` |
| `PARTIAL` | 部分可用，但低于门限 | < `coverage_gate` |
| `MISSING` | 无权威来源 | 0 |

> **PARTIAL 与 MISSING 对算法同等对待**：均触发 `skip`（不补 0、不摊分）。

### 2.3 槽定义示例

```yaml
# slots/slot.cogs.yaml
id: slot.cogs
name: 成本额
source_kind: master_table
source_ref: cost_master.v2
key_strategy: barcode_then_sku          # 完整条码优先，无条码用品牌+精确归一化 SKU 名
coverage_gate: 0.80                     # 低于 80% 视为不可用
freshness: 7d
permission: L4
notes: |
  成本主数据按固定列位解析；表头变化须显式失败，不做模糊匹配。
  未命中保留空值（显示 —），禁止用 0 或均价替代。
```

> **★ `source_kind` 与 `source_ref` 的语义 —— 声明必须可解析，不能是装饰**
>
> | `source_kind` | 含义 | `source_ref` 要求 |
> |---|---|---|
> | `master_table` | 主数据表 | **必填**，指向具体主数据（如 `cost_master.v2`） |
> | `api` | 外部 API | **必填** |
> | `mcp` | MCP 工具 | **必填** |
> | `skill` | 技能 | **必填** |
> | `upload` | 人工上传 | **必填** |
> | `derived` | **派生槽**（由桶/事实表算出，非直接采集） | **可空**；一旦填写，必须是 **fact 表全称/简名** 或 **已物化的桶 ID**，否则是「幽灵引用」 |
>
> **允许值以 `sql/0005` 的 CHECK 约束为事实源**（`master_table` / `api` / `mcp` / `skill` /
> `derived` / `upload`）—— **不含 `db` / `file`**（`admin/plane.go` 的注释曾误列二者，
> 以迁移为准；闸门已断言「迁移允许集合 ⊆ `gate.SlotSourceKinds()`」防两侧漂移）。
>
> **占位符一律拒绝加载**：`todo` / `tbd` / `x` / `-` / `?` / `n/a` / `none` / `待定` / `无`
> 等（归一化大小写/空白/下划线后精确匹配）。反向有「不误伤」纪律：`x_api` / `xray.ads` /
> `tbd_report` / `todo_master` 是**合法** ref（不是占位符）。
>
> **为什么必须判定**：`source_kind` / `source_ref` 此前**被读、被存进 `registry_slot`，
> 却从未被任何断言消费** —— 唯一的校验是 `SourceKind == ""`。于是 `source_ref: x`、
> `source_kind: 想写什么写什么` 一律照过（**声明等于装饰**）。
> 派生槽的 `source_ref` 到底该指向 fact 表还是已物化桶，代码里根本没有答案。
> 闸门首日即抓到真缺陷：`slot.gross_profit` 的 `source_ref: pnl_sku_month` 指向一个
> **并不存在的桶**（唯一桶是 `pnl_month`）。
>
> **装载顺序**：`LoadRegistry`（槽）先于 `LoadBucketRegistry`（桶）—— 派生解析依赖桶，
> 故必须在桶装载后经 `slot.ValidateWithBuckets` **重校验**（`sparkd loadSpecs` 调用）。
> **派生的 `ref` 在桶到位前不做解析**（否则是一段静默放行窗口）；**未解析（nil resolver）
> = 不通过**（fail-closed）。
>
> 判定实现：`gate.CheckSlotSourceResolvable` / `IsPlaceholderRef` / `FactTables`
> + `slot.ResolveDerived` / `ValidateWithBuckets`。详见 `05-验收闸门.md` 的「G4 第六侧」收口。

> **★ `key_strategy` 的语义 —— 声明必须可解析，且跨槽必须一致**
>
> `key_strategy` 回答「**多条来源按什么键合并成一行**」。上表「匹配键」列
> 与 YAML 的 `key_strategy` 是**同一个事实的两种写法**，故：
>
> | `key_strategy` | 匹配键列写法 | 语义 |
> |---|---|---|
> | `direct` | `—` | 整行直达（主数据行即键，不做跨源合并） |
> | `store_sku` | `store+sku` | 店铺 + SKU（渠道流水与成本的默认对齐口径） |
> | `sku` | `sku` | 仅 SKU（库存/物流等以 SKU 为唯一粒度的来源） |
> | `spu` | `spu` | 仅 SPU（达人佣金/市场费用按 SPU 计提） |
> | `channel_day` | `channel+day` | 渠道 + 日期（广告花费按渠道逐日对齐） |
> | `shop_txn` | `shop+txn` | 店铺 + 交易号（平台费用按交易逐笔对齐） |
> | `date_pair` | `date+pair` | 日期 + 货币对（汇率按日、按货币对对齐） |
> | `barcode_then_sku` | `barcode→sku` | 完整条码精确匹配优先，无条码退到品牌+归一化 SKU 名（成本主数据专用） |
>
> **为什么必须判定**：`key_strategy` 此前**被读、被存进 `registry_slot`，
> 却从未被任何断言消费** —— 全链路只有解析/赋值/写库三类用法，**没有第四类**。
> 于是 16 个槽全声明了它，而 `store_sku` 与`随便写`行为完全等价。
> 后果不是「少一条断言」，而是**跨源对齐口径失去判据**：写错它桶照样算出来，
> 但合并后每一行都可能张冠李戴（A 店成本配到 B 店收入上），**全程零报错**。
> 静默的错数，比缺数危险得多。
>
> **★ 共用来源的槽，键口径必须一致**：若两个槽的 `source_kind` + `source_ref` 相同
> 却声明了不同键，则同一来源被按两种口径合并，结果必然对不上。
> 这是「逐条校验都过、合起来是错的」那类缺陷，**单元断言看不见**，
> 故单列一条跨槽判定（`gate.CheckKeyStrategyCohesion`）。
> 例外：`direct`（整行直达）与明细键**允许共存**于同一主表引用下 —— 读法不同不等于冲突。
>
> 判定实现：`gate.CheckKeyStrategyDeclared` / `ParseKeyStrategy` / `CheckKeyStrategyCohesion`
> + `slot.KeyStrategyDocs` → `Validate`（真实生产调用点）。
> 详见 `05-验收闸门.md` 的「G4 第七侧」收口。

> **★ `coverage_gate` 与 `freshness` 是两个不同的问题 —— 两个都必须有判定**
>
> | 字段 | 回答的问题 | 判定落点 |
> |---|---|---|
> | `coverage_gate` | 这一份数据**全不全** | 覆盖率低于门限 ⇒ 槽 `DEGRADED` ⇒ 依赖算法 `skip` |
> | `freshness` | 这一份数据**新不新**（距上次成功采集多久算过期） | 数据龄超过时效 ⇒ 槽 `DEGRADED` ⇒ 依赖算法 `skip` |
>
> **一份覆盖率 100% 但停在三个月前的快照，跑出来的 P&L 是旧的**，
> 而只看覆盖率这一维它是「完好的」—— 这正是 `freshness` 必须参与判活的原因。
>
> **格式**：`<正整数>` + 单位，单位 ∈ {`m` 分, `h` 时, `d` 天, `w` 周}（如 `30m` / `12h` / `1d` / `7d` / `2w`）。
> 自由文本（`daily` / `7天` / `1 day`）、小数（`1.5d`）、`0d` 一律**加载失败** ——
> 它们看似合理，但解析器拿不到时长，判定会退化成「不影响任何事」。
>
> **异常口径（fail-closed）**：**没有新鲜度读数 ⇒ 按过期处理**，不是按新鲜处理。
> 否则采集器整个挂掉这条通道，反而会让所有槽都判活 —— 失效方向恰好反了。
> 龄为负（时钟回拨 / 脏数据）同样按过期处理。
>
> 判定实现：`gate.CheckFreshnessDeclared`（声明层）+ `gate.ParseFreshness`（唯一解析权威）
> + `slot/coverage.go: CheckFreshness / Cases / Judge`（判活）。
> 详见 `05-验收闸门.md` 的「槽的采集时效闭环」（第十三个变种）。

## 3. 算法清单（Algorithm）

### 3.1 算法定义格式

```yaml
id: algo.<name>
name: 中文名
version: <int>                    # ★ 必须为正整数；登记时不得倒退（G4 第十侧，见下）
status: ACTIVE | PENDING         # 可选，缺省 ACTIVE（见下）
formula: <纯公式>
unit: THB | % | count             # ★ 必须可解析、与公式形态相称（G4 第九侧，见下）
permission: L1..L4                # ★ 必须可解析且是 L1/L2/L3/L4 之一（G4 第八侧，见下）
depends_on_slots: [...]          # 数据槽依赖（G4 要求算法与数据源分离）
depends_on_algos: [...]          # 可选：算法依赖算法（链式，见下）
writes_bucket: <bucket_id>
missing_policy: skip | null | error    # ★ 必须可解析；null 须带引号写 "null"（G4 第十三侧，见下）
trace: true
```

#### ★ 缺失策略（`missing_policy`）的**可解析性 + 运行时执行**约定（2026-10-09 新增闸门 / G4 第十三侧）

`algorithms/*.yaml` 的 `missing_policy` 必须是 **`skip` / `null` / `error`** 之一，
并与 `sql/migrations/0002_slots_and_rules.sql` 的
`CHECK (missing_policy IN ('skip','null','error'))` **同源**。语义（本仓定义）：

| 取值 | 依赖值缺失时的行为 |
|---|---|
| `skip` | **跳过该字段**（不写、记入 `skipped_fields`，绝不写 0 冒充） |
| `null` | **显式写 NULL**（该列该行为空，但**不**计入 `skipped_fields`） |
| `error` | **报错**（fail-closed，让构建失败而非静默产出空值） |

- 允许大小写差异（`SKIP` → `skip`）；**不允许别名**：`ignore` / `raise` /
  `skip_if_missing` / 中文 一律**加载失败**。

> ★★ **YAML 保留字陷阱：`null` 必须写成带引号的 `"null"`。**
> 裸写 `missing_policy: null`（以及 `~`、空值）会被 **YAML 解析成空值**，
> 落到 Go 的 string 字段就是空字符串 —— 作者想要的「缺失写 NULL」会被
> 缺省填充**静默改成「跳过」**（语义反转、零报错）。实测（yaml.v3）：
> `null` / `~` / 空 ⇒ `""`；唯有 `"null"` 带引号才得到 `null`。
> 闸门对「键存在但值是 YAML 空值」**单列报错**并提示写 `"null"`。

> ★ 三值在**运行时真的分路执行**（`precomp.BuildRow`）—— 不是「声明了就算」。
> 此前运行时只判 `== "skip"`，`null`/`error`/乱写统统落到同一分支写 NULL
> ⇒ `error` 与 `null` 与乱写**行为完全等价**（声明等于装饰）。

#### ★ 可回溯声明（`trace`）的**可解析性 + 出站可回溯**约定（2026-10-09 新增闸门 / G4 第十四侧）

`algorithms/*.yaml` 的 `trace` 必须是**布尔**（YAML 的 `true` / `false`），
并与 `sql/migrations/0002_slots_and_rules.sql` 的
`trace boolean NOT NULL DEFAULT true` **同源**（缺省 `true`）。

- 只接受真正的布尔：`"true"`（字符串）、`1`（数字）、`yes`/`no` 一律**加载失败**
  （「看起来像布尔但不是」正是「写了等于没写」的入口）。
- **未声明**按缺省 `true` 处理（与 0002 的 `DEFAULT true` 一致）——
  缺省为「可回溯」而不是「不可回溯」：静默变成不可回溯比多回溯危险得多。

> ★ **物化算法必须 `trace: true`。** 一个算法的输出若会被写进桶
> （`writes_bucket` 非空且 `status` 非 `PENDING`），则必须声明 `trace: true` ——
> 否则它的值将**永远追不回是哪条算法算的**，直接违反 `docs/02` 验收
> 「所有输出可沿 `AlgoTrace` 回溯」。

**可回溯的完整链路（三层，缺一即漏）**：

| 层 | 位置 | 断言 |
|---|---|---|
| 声明 | `gate.CheckTraceDeclared` + `slot.Validate` | 物化算法必须 `trace: true`；值必须可判定为布尔 |
| 运行时 | `query.go` 组装 `AlgoTrace` | 从**算法注册表**补齐 `dataSlots`（依赖槽）、`skipped`（桶的 `skipped_fields`）、`reason`（`gaps`）；并**真消费** `trace` 声明（`false` ⇒ 不产出条目） |
| 出站 | `gate.CheckAlgoTraceCoversColumns` + `slot.ContractGuard` | 每条派生列必须有 `AlgoTrace` 条目、`algoId` 与列一致、且 `dataSlots` 非空 |

> ★ 此前 `trace` 是**被读进来、写进 DB（`registry_algorithm.trace`）、
> 但没有任何判定消费其声明值**的一个字段：`precomp.AlgoDef` 根本没有 `Trace` 字段，
> `query.go` 组装 `AlgoTrace` 时也从不看它 ⇒ `trace: true` 与 `false` 与乱写
> **行为完全等价**（第二十二个变种）。
> 更严重的是**输出侧也没被消费**：`AlgoTrace` 只填了 `field`/`algoId`，
> `dataSlots` 永远为空、`skipped` 永远 `false` ⇒ `docs/01 §5.5` 与 `docs/02`
> 验收「可回溯算法与数据槽」在实现侧**做不到**，且没有任何东西会变红。

#### ★ 密级（`permission`）的**可解析性**约定（2026-10-07 新增闸门 / G4 第八侧）

`slots/*.yaml` 与 `algorithms/*.yaml` 的 `permission` 必须是
**`L1` / `L2` / `L3` / `L4`** 之一（`docs/01 §13.3`：L1 公开 / L2 内部 / L3 敏感 / L4 核心），
并与 `sql/migrations/0002_slots_and_rules.sql` 的
`CHECK (permission IN ('L1','L2','L3','L4'))` **同源**。

- 允许大小写差异（`l4` → `L4`，笔误且无歧义）；
- **不允许别名**：`核心`、`高密`、`L4级`、`internal`、`L5` 一律**加载失败**。

> ★ **注意：密级不是沿依赖链单调的，本闸门也刻意不这么断。**
> 实测样例：`algo.cogs` 声明 `L4`，其原料之一 `slot.qty`（销量）声明 `L2` ——
> 「卖了多少件」属内部、而「每件成本多少钱」属核心，**低密级体量原料造出高密级成品
> 在业务上完全正当**；反向亦然（`algo.gp = revenue − cogs`，减法降低敏感度）。
> 若强行要求「算法密级 ≤ 原料槽密级」，只能靠抬高 `slot.qty` 或压低 `algo.cogs`
> 来满足，后者等于**把核心成本降级** —— 那是真正的安全回归。
> 故闸门只钉「档位已知 + 与 DB 词表同源」，**不钉它装不下的东西**。

#### ★ 计量单位（`unit`）的**可解析性与相称性**约定（2026-10-08 新增闸门 / G4 第九侧）

`algorithms/*.yaml` 的 `unit` 必须：

1. **非空且可解析** —— 允许的规范单位是 `THB` / `%` / `count`
   （外加本仓已实际使用、语义无歧义的 `ratio`，与 `%` 归一同一形）；
2. **与 `formula` 的形态相称** —— 「顶层裸名相除」形态的公式（如 `gp / revenue`）
   **不得**声明为金额单位（`THB` / `CNY`）；
3. **与 0002 / 0004 同源** —— 0004 种子里 `registry_algorithm.unit` 的取值
   必须逐个可解析（加载期静态比对，**不连数据库**）。

- 允许大小写差异与已知别名（`percent` / `pct` / `percentage` → `%`，语义完全等价）；
- **不允许自由文本**：`货币` / `元` / `泰铢` / `百分比` / `件` / `THB/件` 一律**加载失败**。

> ★ **为什么必须有这一侧**：`unit` 此前是**被读进来、写进 DB（`registry_algorithm.unit`）、
> 但没有任何判定消费**的一个字段 —— 全链路只有解析 / 赋值 / 写库三类用法，
> **没有第四类**（比较、判定、阈值）。全仓 `grep "\.Unit"` 的非测试命中只有
> `admin_handlers.go` / `plane.go` / `store/admin.go` 三处，**全是序列化与建表**；
> `precomp.AlgoDef.Unit` 更是**结构性死字段**（`BuildRow` 从头到尾没读过它一次）。
> 于是 `unit: THB` 与 `unit: 想写什么写什么` 在加载期行为完全等价。
>
> 后果是**量纲静默失真**（与大数字、汇率、百分比三处叠加时最危险）：
> `algo.gmp`（毛利率）声明的是比率（真实数值 `0.42` 这种），单位字段若被改成
> `THB` 或删掉，下游就失去唯一判据 ⇒ 页面上会出现 `0.42 THB` 这种**静默错误口径**；
> 跨算法聚合（「哪些列可以相加」）本就**只能**靠 `unit` 判断，unit 不可信则可加性整体失效。

> ★ **闸门首日抓出的真缺陷**：`0004_registry_seed.sql` 的种子写
> `algo.rev`/`cogs`/`gp`/`net_contrib` 单位是 `'CNY'`、`algo.gmp` 是 `'ratio'`，
> 而 `algorithms/*.yaml` 写的是 `THB` / `percent` —— **两侧逐字不同**。
> 这不是「种子错了」，而是**两侧各写一份词表**的必然结果：谁也没错、就是不一致。
> 而 `unit` 列在 0002 里是 `text NOT NULL`（**无 CHECK**），加载期此前也无人校验
> ⇒ 分叉可以无限期共存。已按 §4.2「本位币 THB（`rule.fx.base`）」统一为
> `THB` / `%`。

> ★ **本侧刻意不做的一件事：「公式量纲推断」。**
> `Σ(qty × cost_unit)` 得到 `THB` 是**业务约定**，不是表达式能推出来的
> （`qty` 无量纲、`cost_unit` 是 THB/件，乘法才得 THB；而 `revenue - cogs` 与
> `gp / revenue` 的量纲规则又完全不同）。若强行做量纲推断器，等于在仓库里再养一套
> 语义规则，与「单一事实源」纪律冲突；一旦推错，就是把**正确数据判成违规**。
> 故「相称性」判定只做**单向、很窄**的可疑提示（比率公式声明为金额 ⇒ 报），
> 反向（金额公式声明为 `%`）不判 —— 那可能是业务上确实要百分数展示的派生指标，
> 静态看不出来，强行判会误伤。**参 G4 第八侧教训：闸门本身也可能是错的。**

> **下游携带**：`precomp` 已把单位**随单元格产出** —— `CellResult.Unit`（经
> `gate.ParseUnit` 归一，不可解析时保留原文而不静默丢弃）与 `RowResult.Units()`。
> 这让 `unit` 第一次成为**可被下游消费的结构化输出**（决定数值格式与可加性），
> 而不是一个只在表里躺着、没人读的死字段。

#### ★ 版本号（`version`）的**可解析性与不倒退**约定（2026-10-08 新增闸门 / G4 第十侧）

`algorithms/*.yaml` 的 `version` 必须是**正整数**（本文 §3.1 的定义格式），并且：

1. **可解析** —— 纯十进制正整数（如 `3`）。`v3` / `V3` / `3.1` / `3-2` / `latest` /
   `三` / `+3` / `0` / `-1` / 超上界（`> 1000000`，疑似多写一位）一律**加载失败**；
   版本是**数值比较对象**，解析不出来就退化成「不影响任何事」；
2. **登记时不得倒退** —— `admin.Plane.ValidateAlgorithm` 在登记动作里与**既有版本**比较：
   `next < prev` ⇒ 拒绝；`prev==0`（首次登记，无比较基准）⇒ 放行；持平（如仅改注释）⇒ 放行；
3. **与 0002 / 0004 同源** —— 0002 的 `version` 列若写了比「`>0`」更严的 CHECK ⇒ 报
   （避免「加载期放行、入库被拒」）；0004 种子里 `registry_algorithm.version` 列的
   **每个字面量**必须逐个可解析（**按列位取**，不全文扫）。静态比对，**不连数据库**。

> ★ **为什么必须有这一侧**：`version` 看似「处处都在用」（`registry_algorithm.version` 列、
> `VersionDrift`、`AlgoVersions`、`AffectedBuckets` …），但把它的**值**当作被校验对象来看，
> 全链路只有解析 / 赋值 / **逐层搬运**三类用法，**没有第四类**（比较、判定、阈值）：
> 全仓非测试代码里没有一处把 `Algorithm.Version` 与算法身份比较；
> `admin.Plane.ValidateAlgorithm`（唯一的登记入口）对它**零校验**；
> `RegisterAlgorithm` 只在 `Version <= 0` 时静默把它改成 `1` —— 那是**缺省填充，不是校验**；
> 0002 把 `version` 建成 `integer NOT NULL` 且**无 CHECK**。
> 于是 `version: 想写什么写什么` 在加载期与入库期**行为完全等价**。

> 后果是**版本漂移检测静默失真**（G6 的全部结论都建在它上面）：版本号是「改了公式要
> 重算哪些桶」的**唯一判据**；若改公式时忘了 +1，`AffectedBuckets` 返回空 ⇒
> **改了公式却不重算**，报表长期显示错误口径（这比崩溃危险得多）。版本还能**倒退**，
> 让已重算过的桶被判为「版本超前」。

> ★ **本侧刻意不做的一件事：「YAML vs 0004 种子」的身份对平。**
> 实测两侧已**真实分叉**：`algo.cogs` YAML=3 / 种子=2；`algo.gmp` YAML=3 / 种子=1；
> `algo.net_contrib` YAML=2 / 种子=1；`algo.gp` YAML=3 / 种子=3（恰好一致）。
> 但**静态无法判定哪一侧是真相** —— 种子被迁移
> `ON CONFLICT (id) DO UPDATE SET version = EXCLUDED.version` 覆盖，
> YAML 与种子谁先谁后取决于部署动作顺序。若强行断言「必须相等」，
> 就只能靠改数据去迁就一条未经验证的规则（参第八侧 / 第九侧教训：
> **宁少一条真断言，不写一条假断言**）。真实分叉**如实记录**在此处与 `docs/05`，
> 交用户拍板（`docs/06` **F15**）。桶侧的对平由 `VersionDrift` 在**运行时**
> （真注册表 vs 真桶状态）完成 —— 那才是有依据的比对。

> ★ **本侧刻意不做的第二件事：语义化版本解析**（`3.1.2` / `v3`）。
> `version: <int>` 是本文件的定义，放宽写法只会制造第二套解析规则。

#### ★ 公式自由变量的**值绑定**约定（2026-10-07 新增闸门）

`formula` 里的**自由变量必须能被绑定**，否则内核会**静默**取缺失
（`spark-compute` 的 `eval_formula` 对查不到的变量返回 `Scalar::Missing`，**不报错**），
配合 `missing_policy: skip` 就会让该列在**每条数据**上被跳过 —— 全空、零报错。

绑定来源有二，命名约定唯一：

| 来源 | YAML 键 | 变量名 | 例 |
|---|---|---|---|
| 数据槽 | `depends_on_slots` | `BareName(槽 ID)` | `slot.revenue` → `revenue` |
| 上游算法 | `depends_on_algos` 或桶 `produced_by` 中**排在本算法之前**的算法 | `BareName(算法 ID)` | `algo.gp` → `gp` |

> **反面教材（本闸门上线首日实测抓到）**：`algo.gp` 的公式曾写 `rev - cogs`，
> 而依赖槽是 `slot.revenue`（绑出的变量名是 `revenue`）⇒ `rev` 永远取不到值。
> 同类还有 `algo.gmp`（`rev == 0 ? null : gp / rev`）与
> `algo.net_contrib`（`cm2 - overhead_alloc`，两个变量在全仓**无任何定义**）。
> 前两者已修变量名；后者如实标为 `PENDING`（不臆造来源）。
> 静态校验见 `gate.CheckFormulaVariablesBound`，运行时折算见 `precomp.BuildRow`
> （两者共用同一条 `compute.BareName`）。

#### ★ `status: PENDING`（口径未定 / 实现待补）

某些算法的口径仍在决策中（如 `algo.net_contrib` 依赖的 `algo.cm2` /
`overhead_alloc`）。这类算法**如实标 `PENDING`**，其效果是：

* 绑定闸门**不要求**其自由变量可绑定（因为来源本就还没有）—— 但 `formula` 必须非空
  （否则「待补」是一个没有任何内容的空壳，无从判断待补什么）；
* **禁止**它出现在任何桶的 `produced_by` 里（`gate.CheckPendingAlgosNotProducing`）
  —— 一旦入桶，运行时它就是一条恒空的静默列；
* 待口径拍板、来源补齐后改回 `ACTIVE` 并重新入桶。

⇒ 「已知的未完成」由此成为一个**可被断言的状态**，而不是静默通过。

**明细项字段（唯一权威 = `gate.RuleItemKnownKeys()`，2026-10-09 补）**：

| 键 | 含义 | 说明 |
|---|---|---|
| `id` / `name` | 项标识 / 显示名 | 必填 |
| `kind` | 语义标注（如 `threshold`） | 阈值类规则用它区分「费率」与「门限」 |
| `rate` | 费率 | 与 `flat_per_order` 至少一个非空；`0` 会被闸门拒（静默按 0 计提） |
| `flat_per_order` | 每单定额 | 同上 |
| `vat_included` | 是否含税 | 影响口径 |
| `effective_from` / `effective_to` | 生效期**下界 / 上界**（`YYYY-MM-DD`，可空） | 区间 **`[from, to)`**（含起不含止），与 `compute/src/gate.rs::is_effective` 同源 |

> ★ **写进 `items` 的键必须是上表之一**（2026-10-09 补齐，G4 第十五侧）：`yaml.v3`
> 对结构体未声明的键**不报错、只静默丢弃**。此前 Go 侧没有 `EffectiveTo` 字段，
> 于是按本节写法加 `effective_to: 2026-06-01`（期望费率到期）会被**悄悄丢掉**、
> 费率永不到期、全程零报错。现由 `gate.CheckRuleItems`（生产调用点
> `rule.Registry.Validate`）在**加载期**把「契约外的键」与「生效期形态/次序」
> 变成硬失败。上界语义已由 `gate.RuleItemEffective` 固化（`[from, to)`）。

### 4.3 口径切换规则（承袭 KODP 实测结论）

| 口径 | 定义 | 影响 |
|---|---|---|
| **A 参考口径** | Seller Discount 计入营销费用 | 营销费用虚高，易误读为"费用失控" |
| **B Finance 口径** | Seller Discount 作 contra-revenue（收入抵减） | 揭示真实问题是"折扣压缩毛利" |

**KODP 实测（JupJup TH，2026-08/09）**：

| 指标 | 口径 A | 口径 B |
|---|---:|---:|
| 8 月净贡献 | -152,567.19 | **+123.17** |
| 9 月净贡献 | -2,945,788.22 | **-119,826.78** |

> **关键结论**：净收入两口径**完全相同**（折扣本就从 GMV 扣除），
> 只是从"费用侧"搬到"收入侧"展示。**口径切换会完全改变经营解读**，
> 所以规则层必须支持切换，且默认口径须经用户拍板（决策项 D10）。

## 5. 值输出保证流程

对每个请求字段执行（对应 `01-开发文档.md` §5.5）：

```
1. 取字段 → 找算法 (algo_id)
2. 收集 algo.depends_on_slots 中**每个槽**的状态
3. 判定：
   ├─ 全部 AVAILABLE 且覆盖率 ≥ 门限 → 执行公式 → 得值
   └─ 任一 NOT AVAILABLE → 值 = null + 标记 skipped + 记录 reason
4. 写入 AlgoTrace（field, algo_id, slots, skipped, reason）
5. 渲染层：null → 显示「待接入」/「—」
```

**三条铁律（CI 闸门断言）**：
1. 任何非空值必须有对应 `AlgoTrace` 且 `skipped=false`
2. 任何 `skipped=true` 的字段，契约值必须为 `null`
3. 不得出现 `0` 作为缺失占位（`0` 只能是真实计算结果）
