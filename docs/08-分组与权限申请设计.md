## 1. 三件事的关系

```
        ┌──────────────────────── 权限来源（四条并行） ────────────────────────┐
        │                                                                      │
  ① 角色模板（预设）    ② 分组授权（D12）    ③ 管理员逐项勾选（D11）   ④ 申请获批（D14）
        │                    │                      │                        │
        └────────────────────┴──────────┬───────────┴────────────────────────┘
                                        ▼
                             最终 Entitlement（求值引擎）
                                        ▲
                                        │ 受 D13 约束：
                                        │ 「可授出 ⊆ 自身权限」
```

| # | 决策 | 一句话 |
|:--:|---|---|
| D12 | **用户分组** | 把"同一批人的共同权限"抽出来，避免逐个账号重复勾选 |
| D13 | **职权向下覆盖** | 上级能管下级、能批下级；下级不能管上级；平级互不可见 |
| D14 | **权限申请流** | 用户自己在系统里勾选想要的数据权限 → 提交 → 上级批 → 系统自动开通 |

## 2. 用户分组（D12）

### 2.1 数据模型

```ts
export interface UserGroup {
  id: string;                    // grp_xxx
  name: string;                  // 「华东渠道组」
  description?: string;
  /** 组级授权（成员自动继承，取并集） */
  grants: {
    modules: string[];           // module.*
    dimensions: DimensionGrant[];// 维度 + 取值
    maxLevel: "L1" | "L2" | "L3" | "L4";
    canViewBusinessValues: boolean; // 对 IT 组恒 false（D7）
  };
  /** 管理员 */
  owners: string[];              // 账号 ID，可管理本组成员与授权
  createdAt: string;
  updatedAt: string;
}

export interface GroupMembership {
  account: string;
  groupId: string;
  joinedAt: string;
  /** 组内角色：member | owner */
  role: "member" | "owner";
}
```

### 2.2 规则

| 规则 | 说明 |
|---|---|
| 一人多组 | 账号可同时属于多个分组，授权**取并集** |
| 组不含层级 | 分组是平铺集合，不建树（层级由 D13 的职权链承担） |
| 冲突处理 | 组授权与个人勾选冲突 → **DENY 优先**；启用类取并集 |
| 组授权可关 | 某成员可被"退出继承"（局部排除），用于例外 |
| 与模板关系 | 模板给"新账号默认勾什么"；分组给"哪些人共享额外权限" |
| 与申请关系 | 申请单可**指定目标分组**（批量开通），也可指定单账号 |
| 审计 | 建组/改名/改授权/加人/移人 全部落审计 |

### 2.3 交互

1. **分组列表页**：展示每个组的成员数、携带模块数、密级上限。
2. **成员管理**：批量搜索加人、批量移人、导出名单、查看"该组当前实际权限并集"。
3. **组授权编辑**：与账号权限矩阵同一套勾选树（模块→页面→组件；维度→取值）。
4. **生效预览**：「加入该组后，某人将能看到什么」——所见即所得预览。

## 3. 职权向下覆盖（D13）

### 3.1 组织与职权链

```ts
export interface OrgNode {
  account: string;
  /** 直接上级；顶层为 null */
  supervisor: string | null;
  /** 职权层级：T1 最高，T6 最低 */
  tier: "T1" | "T2" | "T3" | "T4" | "T5" | "T6";
  /** 是否具备审批职责 */
  canApprove: boolean;
}
```

### 3.2 覆盖规则（授权上界约束）

```
可授出集合(账号 A) ⊆ 账号 A 自身权限集合        ← 核心不变量
```

| 规则 | 说明 |
|---|---|
| 向下覆盖 | A 只能为其**下级**（supervisor 链上可达）授予权限 |
| 不得反向 | 下级不能给上级授予任何权限 |
| 平级隔离 | 同级默认互不可见、互不可审批；除非被显式指定为**协办审批人** |
| 不得溢出 | A 授予 B 的权限，**不得包含 A 自己没有的权限**（防止横向/纵向提权） |
| 越级兜底 | 跨部门 / 跨枝申请，路由到**最近公共上级**；无则 T1 兜底 |
| 密级约束 | A 的密级上限 ≥ 被授出权限的密级上限 |
| 特殊：D7 | 任何情况下，任何账号**都不能**授予 IT 角色业务数值权限（IT 恒不可见） |
| 特殊：ADMIN | T1 总管理员可管理全组织，但仍受 D7 约束 |

### 3.3 审批路由算法

```
输入：申请人 U、申请集合 S
1. 若 S 超出 U 自身可申请范围（业务数值对 IT）→ 直接拒绝并说明原因
2. 找 P = U 的 supervisor
3. 若 P 不存在（U 为顶层）→ 路由到 T1（ADMIN）
4. 若 P 存在，且 S ⊆ 权限(P) → P 审批
5. 若 S ⊄ 权限(P)（P 权限不足以批准）→ 向上一级找最近的、其权限 ⊇ S 的上级
6. 若到顶仍无 → 由 T1 审批（T1 作为域的超集兜底）
```

> 原则：**审批人必须自己拥有被申请的全部权限**，否则无权批出。

## 4. 权限申请流（D14）

### 4.1 申请单模型

```ts
export interface PermissionRequest {
  id: string;                    // req_xxx
  applicant: string;             // 申请人账号
  /** 申请内容 = 一份 Entitlement 草案 */
  draft: {
    modules: string[];
    dimensions: DimensionGrant[];
    maxLevel: "L1" | "L2" | "L3" | "L4";
  };
  /** 也可批量：给某个分组申请 */
  targetGroupId?: string;
  /** 用途说明（必填） */
  purpose: string;
  /** 期望有效期；空 = 长期 */
  requestedExpiry?: string;
  status: "DRAFT" | "SUBMITTED" | "APPROVING" | "APPROVED" | "REJECTED" | "WITHDRAWN";
  /** 审批链 */
  approvals: {
    approver: string;
    tier: string;
    action: "APPROVE" | "REJECT" | "RETURN";
    reason?: string;
    at?: string;
  }[];
  createdAt: string;
  resolvedAt?: string;
}
```

### 4.2 全流程

```
① 用户进入「权限申请」页
   ↓  以勾选树呈现可选的数据权限（模块 → 页面 → 组件；维度 → 取值）
   ↓  已拥有的项自动置灰（去重）；不可申请的项（IT 申请业务数值）置灰并注明
② 用户勾选 → 填用途说明 + 期望有效期 → 提交
   ↓  系统校验：是否超出可申请范围？是否与他人冲突？
③ 路由到审批人（§3.3 算法）
   ↓  审批人看到：申请人 / 申请内容 / 用途 / 生效预览（"批了之后此人能看到什么"）
④ 审批人 同意 / 拒绝 / 退回补充
   ↓  支持多级审批（按额度或密级分级，配置见 F7）
⑤ 通过 → 系统**自动写入 Entitlement**（含时间盒）→ 即时开通
   ↓  拒绝 / 退回 → 记录理由，用户可补充后重提
⑥ 到期 → 临时授权自动回收 → 留审计
```

### 4.3 校验规则

| 校验 | 失败处理 |
|---|---|
| 是否超出申请人可申请范围 | 拒绝提交，置灰并注明（如 IT 申请业务数值） |
| 是否重复已有权限 | 自动去除重复项，提示"已拥有" |
| 是否超出审批人可批范围 | 自动升级审批路由（§3.3 第 5 步） |
| 时间盒是否合理 | 临时授权必须 ≤ 上限（默认 90 天，可配） |
| 密级是否合规 | 高密级（L4）默认需 T1 终审 |

### 4.4 与 D11 的关系

- **管理员直接勾选**（D11）：管理员主动授予，无需申请流。
- **用户自助申请**（D14）：用户发起，审批后自动开通。
- 两条路径**并存**，最终都落到同一张 `Entitlement` 表，同一套求值引擎。
- 管理员也可**代用户发起申请**（当用户不具备系统访问条件时）。

## 6. 闸门补充（对应 `docs/05` G7）

| 断言 | 说明 |
|---|---|
| 代授不溢出 | 注入"下级权限 ⊄ 上级权限"的代授，断言被拒 |
| 平级不可互批 | 同级账号提交申请，断言不进该同级审批队列 |
| 分组 DENY 优先 | 组授权与个人禁用冲突时取 DENY |
| 申请未批不通 | 未走完审批的 Entitlement 不生效 |
| IT 恒不可见业务数值 | 无论谁申请/审批，IT 的 `canViewBusinessValues` 恒 false |
| 到期必回收 | 时间盒过期后权限自动失效 |
