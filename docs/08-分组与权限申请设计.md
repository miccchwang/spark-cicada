# 08 · 用户分组 · 职权覆盖 · 权限申请流

> 落地 **D12 / D13 / D14**（2026-10-05 第二轮拍板）+ 二轮补充：**勾选组（数据用途组）**、
> **跨部门可覆盖但需最高权限批准且不可自助申请**、**数据链 / 审批链（+1 审批 + +2 抄送）**。
> 与 `docs/07-账号权限勾选设计.md`（D11）配套：07 讲"管理员如何勾选"，08 讲"分组如何承载 + 用户如何自助申请 + 审批如何流转"。

## 1. 三件事的关系

```
        ┌──────────────────────── 权限来源（四条并行） ────────────────────────┐
        │                                                                      │
  ① 角色模板（预设）    ② 分组授权（D12）    ③ 管理员逐项勾选（D11）   ④ 申请获批（D14）
        │                    │                      │                        │
        └────────────────────┴──────────┬───────────┴────────────────────────┘
                                        ▼
                             最终 Entitlement（求值引擎）
                                        ▲
                                        │ 受 D13 约束：
                                        │ 「可授出 ⊆ 自身权限」
                        跨部门授予 → 仅管理员直接勾选（T1 批准，不可自助申请）
```

| # | 决策 | 一句话 |
|:--:|---|---|
| D12 | **用户分组** | 把"同一批人的共同权限"抽出来，避免逐个账号重复勾选 |
| D13 | **职权向下覆盖** | 上级能管下级、能批下级；下级不能管上级；平级互不可见 |
| D14 | **权限申请流** | 用户自己在系统里勾选想要的数据权限 → 提交 → 上级批 → 系统自动开通 |
| ★ | **勾选组** | 运营数据 / 成本与利润 / 库存与预警 / 投资与回报（详见 `docs/07` §5.5） |
| ★ | **跨部门** | 可覆盖，但需 T1 批准，且不可自助申请（§3.4） |
| ★ | **两套链路** | 数据链（数据归谁）+ 审批链（+1 审批 / +2 抄送）（§3.3） |

## 2. 用户分组（D12）

### 2.1 数据模型

```ts
export interface UserGroup {
  id: string;                    // grp_xxx
  name: string;                  // 「华东渠道组」
  description?: string;
  /** 组级授权（成员自动继承，取并集） */
  grants: {
    modules: string[];           // module.*
    dimensions: DimensionGrant[];// 维度 + 取值
    maxLevel: "L1" | "L2" | "L3" | "L4";
    canViewBusinessValues: boolean; // 对 IT 组恒 false（D7）
  };
  /** 管理员 */
  owners: string[];              // 账号 ID，可管理本组成员与授权
  createdAt: string;
  updatedAt: string;
}

export interface GroupMembership {
  account: string;
  groupId: string;
  joinedAt: string;
  /** 组内角色：member | owner */
  role: "member" | "owner";
}
```

### 2.2 规则

| 规则 | 说明 |
|---|---|
| 一人多组 | 账号可同时属于多个分组，授权**取并集** |
| 组不含层级 | 分组是平铺集合，不建树（层级由 D13 的职权链承担） |
| 冲突处理 | 组授权与个人勾选冲突 → **DENY 优先**；启用类取并集 |
| 组授权可关 | 某成员可被"退出继承"（局部排除），用于例外 |
| 与模板关系 | 模板给"新账号默认勾什么"；分组给"哪些人共享额外权限" |
| 与申请关系 | 申请单可**指定目标分组**（批量开通），也可指定单账号 |
| 审计 | 建组/改名/改授权/加人/移人 全部落审计 |

### 2.3 交互

1. **分组列表页**：展示每个组的成员数、携带模块数、密级上限。
2. **成员管理**：批量搜索加人、批量移人、导出名单、查看"该组当前实际权限并集"。
3. **组授权编辑**：与账号权限矩阵同一套勾选树（模块→页面→组件；维度→取值）。
4. **生效预览**：「加入该组后，某人将能看到什么」——所见即所得预览。

## 3. 职权向下覆盖（D13）

### 3.1 组织与职权链

```ts
export interface OrgNode {
  account: string;
  /** 直接上级；顶层为 null */
  supervisor: string | null;
  /** 职权层级：T1 最高，T6 最低 */
  tier: "T1" | "T2" | "T3" | "T4" | "T5" | "T6";
  /** 是否具备审批职责 */
  canApprove: boolean;
}
```

### 3.2 覆盖规则（授权上界约束）

```
可授出集合(账号 A) ⊆ 账号 A 自身权限集合        ← 核心不变量
```

| 规则 | 说明 |
|---|---|
| 向下覆盖 | A 只能为其**下级**（supervisor 链上可达）授予权限 |
| 不得反向 | 下级不能给上级授予任何权限 |
| 平级隔离 | 同级默认互不可见、互不可审批；除非被显式指定为**协办审批人** |
| 不得溢出 | A 授予 B 的权限，**不得包含 A 自己没有的权限**（防止横向/纵向提权） |
| 密级约束 | A 的密级上限 ≥ 被授出权限的密级上限 |
| **跨部门可覆盖** | 跨部门**允许**覆盖（上级可管其职权链上跨部门的成员），**但必须最高权限批准**（见 §3.4） |
| 特殊：D7 | 任何情况下，任何账号**都不能**授予 IT 角色业务数值权限（IT 恒不可见） |
| 特殊：ADMIN | T1 总管理员可管理全组织，但仍受 D7 约束 |

### 3.3 数据链与审批链（两套链路）★ 二轮新增

本项目区分两条**不同**的链路，不可混为一谈：

| 链路 | 定义 | 决定什么 |
|---|---|---|
| **数据链**（Data Chain） | 一份数据**归属谁、由谁负责**（责任人链） | 谁能看到该数据；跨部门时该找谁 |
| **审批链**（Approval Chain） | 一次申请/变更**由谁批、抄送给谁** | 申请走给谁、抄送给谁 |

#### 3.3.1 数据链人员（Data Chain Owners）

每条数据（渠道 / 店铺 / 品牌 / 品类）都有明确的责任人链：

```ts
export interface DataChainNode {
  /** 数据范围标识，如 channel:TK-TH / store:S123 / brand:KONVY */
  scope: string;
  /** 数据责任人（该数据的业务 owner） */
  owner: string;
  /** 责任人的上级链（用于跨部门时找共同上级） */
  ownerChain: string[];        // [owner, owner.supervisor, …, T1]
  /** 部门 */
  dept: string;
}

export interface DataChain {
  /** 该数据范围的责任链 */
  nodes: DataChainNode[];
  /** 部门归属 */
  depts: string[];
  /** 是否跨部门（由多个部门共同负责） */
  crossDept: boolean;
}
```

**规则**：
- **数据链決定「可见边界」**：只有落在申请数据链上的人（或其上级）才可能被批准。
- **数据链決定「跨部门判定」**：若申请的数据范围跨越 ≥2 个部门 → 触发跨部门规则（§3.4）。
- 数据链是**静态配置 + 动态推导**：部门/上级关系变更时自动重算。

#### 3.3.2 审批链人员（Approval Chain）

用户明确：**「审批链条由 +1 审批，同时同步抄送 +2 或者 +1 的直属上级」**。

```
+1  = 申请人的直接上级（审批人）
+2  = 申请人的上级的上级（抄送人）

        ┌────────────────────────────────────┐
申请人 U ─┤ +1 = U.supervisor        → 审批  │
        │ +2 = U.supervisor.supervisor → 抄送 │
        └────────────────────────────────────┘
  若 +2 不存在（+1 已是顶层）→ 抄送 +1 的直属上级（若有）
```

| 角色 | 是谁 | 动作 |
|---|---|---|
| **审批人（+1）** | 申请人的直接上级 | **同意 / 拒绝 / 退回**（唯一有决定权的人） |
| **抄送人（+2）** | 申请人 +2，或 +1 的直属上级 | **知会**（可见该申请，通常不阻断；可设为"会签"则可否决） |

```ts
export interface ApprovalChain {
  applicant: string;
  /** 审批层：+1，唯一决定权 */
  approver: string;              // = applicant.supervisor
  approverTier: string;
  /** 抄送层：+2 或 +1 的直属上级 */
  ccList: string[];              // [applicant.supervisor.supervisor] 或 [approver.supervisor]
  /** 若申请人已是 T1（无 +1），则 +1 取 T1 兜底，抄送为空 */
  fallback?: boolean;
}
```

#### 3.3.3 审批路由算法（修订版）

```
输入：申请人 U、申请集合 S
1. 解析 S 的数据链 → 得涉及的部门集合 D(S)、责任人链
2. 若 S 超出 U 自身可申请范围（如 IT 申请业务数值）→ 直接拒绝并说明
3. 若 D(S) 跨越 ≥2 个部门（跨部门）→ 走 §3.4 跨部门分支
4. 否则（本部门内）：
   a. 审批人 = U.supervisor（+1）
   b. 若 U.supervisor 不存在（U 为顶层）→ 审批人 = T1 兜底
   c. 校验：S ⊆ 权限(审批人) ？若不满足 → 沿上级链上溯，找最近的权限超集者
   d. 抄送人 = U.supervisor.supervisor（+2）
      若 +2 不存在 → 抄送 = U.supervisor.supervisor 的上级（+1 的直属上级）
      若仍不存在 → 抄送为空
5. 输出：{ approver: +1, ccList: [+2 或 +1 的直属上级] }
```

> 原则：**审批人必须自己拥有被申请的全部权限**，否则无权批出；
> 抄送人只需**知会**，不需拥有该权限（但若配置为会签，则需要）。

### 3.4 跨部门覆盖：可覆盖，但需最高权限批准，且不可自助申请 ★ 二轮新增

用户明确：**「跨部门可覆盖，但是需要最高权限批准不可申请」**。

| 规则 | 落地 |
|---|---|
| **允许覆盖** | 跨部门的数据可被覆盖授予（不是硬禁止） |
| **必须最高权限批准** | 跨部门授予**必须 T1 总管理员批准**（+1 无权单独批准跨部门） |
| **不可自助申请** | 跨部门权限**不出现在用户自助申请页**；用户勾选不到、无法提交 |
| **仅管理员直接授予** | 只能由 **T1 管理员在权限矩阵中主动勾选授予**（走 D11，不走 D14） |
| **全程留痕** | 跨部门授予必须记录：授予人、被授人、跨了哪些部门、理由 |

```
判断是否跨部门：
  depts(S) = 申请/授予涉及的全部数据所属部门
  若 |depts(S)| ≥ 2  →  跨部门  →  需 T1 批准 + 不可自助申请
  否则               →  本部门  →  +1 审批即可（§3.3.2）
```

**自助申请页的行为**：
- 跨部门数据项在勾选树中**置灰不可勾选**，旁注「跨部门权限需 T1 管理员直接授予」。
- 用户若确有跨部门需求 → 只能线下/走其他流程找 T1，由 T1 在矩阵中直接勾选。

### 3.5 审批链与数据链的对应关系（示例）

设申请人 U 负责渠道 `TK-TH`（部门：TK 运营组），想申请店铺 `S123` 的运营数据。

| 情形 | 数据链 | 审批链（+1 审批 / +2 抄送） | 结果 |
|---|---|---|---|
| 同部门 | `S123` 属 TK 运营组 | +1 = U 上级；+2 抄送 | ✅ +1 批准即可 |
| 跨部门 | `S123` 属 Shopee 运营组 | +1 无从批准 | ⛔ 需 T1 批准；**U 不能自助申请**，只能 T1 直接授予 |
| U 是顶层 | U = T1 | +1 取 T1 兜底；抄送空 | ✅ T1 自批（留痕） |

## 4. 权限申请流（D14）

### 4.1 申请单模型

```ts
export interface PermissionRequest {
  id: string;                    // req_xxx
  applicant: string;             // 申请人账号
  /** 申请内容 = 一份 Entitlement 草案（含勾选组） */
  draft: {
    dataUseGroups: GroupScopeGrant[];   // 四个勾选组（§07 §5.5）
    modules: string[];
    dimensions: DimensionGrant[];
    maxLevel: "L1" | "L2" | "L3" | "L4";
  };
  /** 也可批量：给某个分组申请 */
  targetGroupId?: string;
  /** 用途说明（必填） */
  purpose: string;
  /** 期望有效期；空 = 长期 */
  requestedExpiry?: string;
  status: "DRAFT" | "SUBMITTED" | "APPROVING" | "APPROVED" | "REJECTED" | "WITHDRAWN" | "BLOCKED_CROSS_DEPT";
  /** 数据链解析结果（决定可见边界与是否跨部门） */
  dataChain?: {
    scopes: string[];
    depts: string[];
    crossDept: boolean;
  };
  /** 审批链：+1 审批，+2 或 +1 的直属上级抄送 */
  approvalChain: ApprovalChain;
  /** 审批动作记录 */
  approvals: ApprovalStep[];
  createdAt: string;
  resolvedAt?: string;
}
```

### 4.2 全流程

```
① 用户进入「权限申请」页
   ↓  以勾选树呈现：四个勾选组 → 组内字段/维度
   ↓  已拥有的项置灰；**跨部门项置灰并注明「需 T1 直接授予」**
   ↓  IT 账号的业务数值项置灰（D7）
② 用户勾选 → 填用途说明 + 期望有效期 → 提交
   ↓  系统校验：
   ↓    · 是否超出可申请范围（IT 业务数值 / 跨部门）
   ↓    · 解析数据链 → 判定是否跨部门
   ↓    · 去重已有权限
③ 路由审批链（§3.3.3）：
   ↓  审批人 = +1；抄送 = +2 或 +1 的直属上级
   ↓  若跨部门 → 状态置 BLOCKED_CROSS_DEPT，提示"需 T1 直接授予"
④ 审批人（+1）同意 / 拒绝 / 退回补充；抄送人（+2）收到知会
   ↓  审批人看到：申请人 / 申请内容 / 用途 / 数据链 / 生效预览
⑤ 通过 → 系统**自动写入 Entitlement**（含时间盒）→ 即时开通
   ↓  拒绝 / 退回 → 记录理由，用户可补充后重提
⑥ 到期 → 临时授权自动回收 → 留审计
```

### 4.3 校验规则

| 校验 | 失败处理 |
|---|---|
| 是否超出申请人可申请范围 | 拒绝提交，置灰并注明（如 IT 申请业务数值） |
| **是否跨部门** | **状态置 `BLOCKED_CROSS_DEPT`；提示需 T1 直接授予；不进自助审批流** |
| 是否重复已有权限 | 自动去除重复项，提示"已拥有" |
| 是否超出审批人（+1）可批范围 | 沿上级链上溯找权限超集者（§3.3.3 第 4c 步） |
| 时间盒是否合理 | 临时授权必须 ≤ 上限（默认 90 天，可配） |
| 密级是否合规 | 高密级（L4）默认需 T1 终审 |

### 4.4 与 D11 的关系

- **管理员直接勾选**（D11）：管理员主动授予，无需申请流。**跨部门权限只能走这条**。
- **用户自助申请**（D14）：用户发起，+1 审批后自动开通。**仅限本部门**。
- 两条路径**并存**，最终都落到同一张 `Entitlement` 表，同一套求值引擎。
- 管理员也可**代用户发起申请**（当用户不具备系统访问条件时）。

## 6. 闸门补充（对应 `docs/05` G7）

| 断言 | 说明 |
|---|---|
| 代授不溢出 | 注入"下级权限 ⊄ 上级权限"的代授，断言被拒 |
| 平级不可互批 | 同级账号提交申请，断言不进该同级审批队列 |
| 分组 DENY 优先 | 组授权与个人禁用冲突时取 DENY |
| 申请未批不通 | 未走完审批的 Entitlement 不生效 |
| IT 恒不可见业务数值 | 无论谁申请/审批，IT 的 `canViewBusinessValues` 恒 false |
| 到期必回收 | 时间盒过期后权限自动失效 |
| **+1 审批 / +2 抄送** | 申请提交后，仅 +1 进审批队列；+2（或 +1 的直属上级）进抄送列表 |
| **跨部门不可自助** | 跨部门数据项在自助申请页置灰，提交时状态置 `BLOCKED_CROSS_DEPT` |
| **跨部门须 T1** | 注入"非 T1 批准跨部门授予"，断言被拒 |
| **数据链判定正确** | 给定数据范围，断言解析出的部门集合与 `crossDept` 正确 |
| **勾选组依赖** | 勾 `grp.roi` 而无 `grp.cost_profit`+`grp.inventory` 时提示/降级 |
