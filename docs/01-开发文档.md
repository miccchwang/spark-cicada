## 0. 本版要解决的七个问题（需求原文 → 架构决策对照）

| # | 需求原文要义 | 架构决策 | 章节 |
|---|---|---|---|
| 1 | 时间区间滑块 + 表格筛选**作为一个模块**，把该模块**状态作为参数提供给 DB**，由**渲染模块接收数据直接渲染** | 引入 **QueryState 协议**：筛选模块只产出状态对象，DB 层消费状态，渲染层是纯函数 | §3 |
| 2 | 区分功能模块，完善角色划分，**最优语言选型** | 模块边界 + 语言选型矩阵（Rust 计算内核 / Go 服务 / TS 前端） | §2 §4 |
| 3 | 围绕 DB 形成**前置算法规则与运算法则**，避免每次重新运算 | **预计算层（Precompute Layer）**：规则/公式落成 DB 物化视图与增量桶 | §5 |
| 4 | **算法与数据来源分开**，暂无的数据跳过，保证每个值都能基于现有数据算出 | 算法注册表（Algorithm Registry）+ 数据源可用性门控 | §5.3 §5.5 |
| 5 | IT 后台直接管理**所有 MCP 及 API 授权与状态**、账号启用状态 | **Integration Control Plane**（集成控制面）独立模块 | §6 |
| 6 | **可自迭代自优化的算法模型**，给用户专门区域做决策/策略调整，**以选型方式提供** | **Strategy Lab**（策略实验室）+ 选型式交互 + 反馈闭环 | §7 |
| 7 | 预留其他功能模块接入，从 UI/UX 到功能组合与升级对接形成**灵活分布与调整** | **插槽架构（Slot Architecture）**：模块清单 + 能力声明 + 组合规则 | §8 |
| 8 | 经营报表与 P&L 区分模块，按信息概括程度形成**阅览层级** | **L0 总览 → L1 板块 → L2 渠道 → L3 店铺 → L4 SKU** 五层 | §9 |
| 9 | 报表与渠道/店铺层级可**跳转或展开**，所有可收起表格**默认收起** | 层级路由 + 默认收起契约 | §9.4 |
| 10 | 基于用户习惯与当前页面设置形成**可自命名模板** | **View Template** 模块（个人 / 团队 / 系统三档） | §10 |
| 11 | 整体打开速度**毫秒级响应**，渲染与运算深度优化 | 性能预算 + 分层缓存 + 预计算（§5 已覆盖大部分） | §11 |

### 1.1 关键分层原则

| 原则 | 说明 | 反例（KODP 中存在的问题） |
|---|---|---|
| **单一方向依赖** | L5→L4→L3→L2→L1→L0，上层只读下层，永不反向 | 前端自己推导渠道分级（KODP 已整改为只消费） |
| **状态与执行分离** | 筛选模块只产出 `QueryState`，不执行查询 | 筛选逻辑与渲染耦合在同一个 6917 行文件里 |
| **算法与数据分离** | 算法的**法则**与**数据来源**是两个正交维度 | 算法里硬编码数据源，源缺失就整块失败 |
| **预计算优先** | 能被 DB 预先算好的，绝不在请求时重算 | 每次请求重跑整月聚合 |
| **契约化** | 层与层之间用带版本号的契约通信，可独立替换 | 全局共享可变对象 |

## 3. 核心设计一：筛选模块 → DB 参数 → 渲染模块

这是需求第 1 条的直接落地，也是全项目**最重要的解耦**。

### 3.1 三段式数据流

```
┌─────────────────┐   QueryState    ┌──────────────┐   DataContract   ┌──────────────┐
│  M-FILTER       │ ──────────────► │  M-QUERY     │ ───────────────► │  M-RENDER    │
│  (筛选/时间滑块) │                 │  (翻译为查询) │                  │  (纯渲染)     │
└─────────────────┘                 └──────────────┘                  └──────────────┘
   只产出状态                          只翻译状态                        只消费数据
   不查库、不渲染                       不含业务规则                       不含业务计算
```

**关键约束（写进 CI 闸门）**：

1. `M-FILTER` 的产物必须是**可序列化的纯数据**（JSON），不含函数、DOM 引用、闭包。
2. `M-RENDER` 的入参只能是 `DataContract`，**禁止**在渲染层读 `QueryState` 做换算。
3. `M-QUERY` **禁止**包含业务公式（如毛利率、净利率），公式一律来自 `M-ALGO`。

### 3.2 QueryState 协议（唯一筛选契约）

```ts
// contracts/query-state.ts  —— v1.0
export interface QueryState {
  v: "1.0";                              // 协议版本，破坏性变更才升
  time: TimeRange;                       // 时间模块状态（对应滑块）
  filters: FilterClause[];               // 表格筛选状态
  dims: DimSelection;                    // 维度选择（品牌/渠道/店铺…）
  order?: OrderClause;                   // 排序
  page?: PageClause;                     // 分页
  precomputeHint?: PrecomputeHint;       // 提示可命中的预计算桶
  profileId?: string;                    // 来源模板（§10）
}

export interface TimeRange {
  mode: "preset" | "custom" | "slider";
  preset?: "today" | "last7d" | "last30d" | "mtd" | "last_full_month" | "ytd" | "all";
  from?: string;                         // ISO date，mode=slider/custom 时必填
  to?: string;
  grain: "day" | "week" | "month" | "quarter" | "half" | "year";
  timezone: string;                      // 默认门店所在地时区
}

export interface FilterClause {
  field: string;                         // 字段 key，不是列名
  op: "eq" | "in" | "gt" | "gte" | "lt" | "lte" | "between" | "contains";
  value: unknown;
}
```

> **为什么把时间模块与表格筛选合成一个模块**：它们共同决定「查什么数据」，
> 拆成两个模块会导致状态同步、边界重叠、重复请求。合成一个 `M-FILTER` 后，
> 任何界面形态（滑块、下拉、chips、日历）都只是**同一个 QueryState 的不同编辑器**。

### 3.3 DataContract 协议（唯一渲染契约）

```ts
// contracts/data-contract.ts —— v1.0
export interface DataContract<T = Row> {
  v: "1.0";
  queryHash: string;                     // 由 QueryState 规范化后哈希，缓存键
  rows: T[];
  columns: ColumnDef[];                  // 列定义（含密级门控结果）
  aggregates: Record<string, number|null>;
  levels: LevelSummary[];                // 五层阅览层级数据（§9）
  algoTrace: AlgoTrace[];                // 每个值由哪条法则算出（可追溯）
  gaps: DataGap[];                       // 缺失数据（显示"待接入"）
  precomputed: boolean;                  // 是否命中预计算，供性能审计
  generatedAt: string;
}

export interface AlgoTrace {
  field: string;
  algoId: string;                        // 命中的算法 ID
  dataSlots: string[];                   // 实际用到的数据槽
  skipped: boolean;                      // 数据不足而被跳过
  reason?: string;
}
```

### 3.4 状态 → 参数 → DB 的翻译示例

| 用户操作 | QueryState 变化 | M-QUERY 产出 |
|---|---|---|
| 拖动时间滑块到 9/1–9/30 | `time={mode:"slider",from:"2026-09-01",to:"2026-09-30",grain:"day"}` | 命中预计算桶 `pnl_daily:2026-09` |
| 勾选「TK-TH」渠道 | `filters=[{field:"channelCode",op:"eq",value:"TK-TH"}]` | 追加 WHERE，桶内二次过滤 |
| 按毛利率降序 | `order={field:"gmp",dir:"desc"}` | ORDER BY，分页下推 |
| 切到店铺层级 | `dims.level="store"` | 读 `pnl_store_month` 而非 `pnl_sku` |

**性能性质**：因为预计算层已把常用组合算好（§5），`M-QUERY` 在多数情况下退化为
「查一张已聚合好的表 + 加索引过滤」，这是毫秒级响应的基础（§11）。

## 4. 语言选型

### 4.1 选型矩阵

| 层 / 模块 | 语言 | 理由 | 备选与否决 |
|---|---|---|---|
| 计算内核 `M-ALGO` `M-PRECOMP` `M-RULE` | **Rust** | 毫秒级批量运算、无 GC 抖动、WASM 可复用到前端、类型强 | ~~Python~~（KODP 用 Python，批量重算时慢且难保证数值一致性）；~~Node~~（浮点与大数组性能不足） |
| 服务 / 编排 `M-QUERY` `M-SLOT` `M-AUTH` `M-AUDIT` `M-COLLECT` `M-ADMIN`(后端) | **Go** | 高并发、部署简单（单二进制）、生态成熟、KODP 已验证可用 | ~~Rust~~（开发速度慢于 Go，此层无极致性能需求） |
| 前端 `M-FILTER` `M-RENDER` `M-REPORT` `M-PNL` `M-TEMPLATE` | **TypeScript** | 类型安全、契约可编译期校验、组件生态 | ~~JS~~（无类型契约）；框架选型见 §4.2 |
| 计算前端加速 | **Rust → WASM** | 把小粒度即时运算（如滑块拖动中的实时重算）下放到 WASM，避免网络往返 | — |
| DB | **PostgreSQL 15+** | 物化视图、窗口函数、CTE 聚合能力强，适合预计算 | ~~SQLite~~（并发与物化视图能力不足，仅本地开发可用） |
| 缓存 | **Redis** | 查询结果缓存、QueryState 去重、预计算失效通知 | — |
| 采集脚本 | **Go** | 与 `M-COLLECT` 同栈，复用 HTTP 客户端与重试逻辑 | ~~Python 脚本~~（依赖环境，部署脆弱） |

> **语言选型的核心判据**：**热点在运算，不在框架**。所以把「重算」下沉到 Rust，
> 把「编排」留给 Go，把「交互」交给 TS。三层各用其长，不搞单一语言的教条统一。

### 4.2 前端框架与渲染策略

| 项 | 选型 | 理由 |
|---|---|---|
| 框架 | 轻量响应式（如 Solid/Svelte，或 TS + 手写细粒度更新） | **毫秒级首屏**要求下，避免重型虚拟 DOM diff |
| 表格 | 虚拟滚动 + 列级增量渲染 | 万行表格只挂载可视区 |
| 图表 | SVG（轻量） + Canvas（大数据量） | 小图 SVG 便于交互，大图 Canvas 保帧率 |
| 状态 | 单一 `QueryState` store，订阅式更新 | 与 §3 的三段式配套 |
| 构建 | Vite（产物 gzip 后目标 < 200KB 首屏） | — |

> 明确**不引入**重型 UI 库全家桶（KODP 的 `index.html` 6917 行、450KB 已接近维护极限）。

### 4.3 UI/UX 预留设计（需求第 7 条）

从架构第一行代码就预留，而不是后期改造：

| 预留点 | 设计 | 收益 |
|---|---|---|
| 布局槽位 | 页面 = 网格容器，区块通过 `slot` 声明占位 | 新模块**不改布局代码**即可挂载 |
| 导航槽位 | 侧边栏/顶栏 from `SlotManifest` 动态生成 | 新功能自动出现在导航 |
| 设置槽位 | 每模块自带 `SettingsPanel` 声明 | 设置页自动聚合 |
| 数据槽位 | 模块声明需要哪些 `DataSlot`（§5.4） | 数据不足时模块自动降级而非崩溃 |
| 权限槽位 | 模块声明所需密级，权限引擎统一裁决 | 新增模块不遗漏权限 |

## 5. 核心设计二：算法前置与预计算（围绕 DB 的运算法则）

这是需求第 3、4 条的直接落地。

### 5.0 问题定义（为什么必须前置）

KODP 的取数链路是**请求时计算**：

```
请求 → 拉原始数据 → 内存聚合 → 投影 → 返回 → （下次请求再算一遍）
```

问题：
1. 同一份数据被反复计算（每个用户、每次刷新）；
2. 运算逻辑与数据拉取耦合，改算法要重拉数据；
3. 数据源缺失时整块失败，而不是局部降级。

### 5.1 前置架构：一次算好，多处消费

```
数据落地 ──► 规则引擎(Rule Engine) ──► 算法执行(Algorithm) ──► 预计算桶(Materialized)
   │                  │                        │                      │
 原始层            口径/费率/阈值           法则库(可版本化)         增量更新
                                                                      │
                                            ◄─────────────────────────┘
                                            请求时只做「读 + 过滤 + 排序」
```

### 5.2 预计算桶（Precompute Bucket）设计

| 桶 ID | 粒度 | 刷新触发 | 服务于 |
|---|---|---|---|
| `pnl_daily` | 日期 × 渠道 × 店铺 | 每日增量 | 日/周趋势 |
| `pnl_month` | 月 × 渠道 × 店铺 × 品牌 | 每月 + 补数 | 经营报表主表 |
| `pnl_sku_month` | 月 × SKU | 每月 | SKU 明细 |
| `stock_snapshot` | 时点 × SKU × 仓 | 每日 | 库存/预警 |
| `channel_rollup` | 渠道 × 品牌 × SPU × SKU | 每日 | 渠道销售 |
| `kpi_summary` | 月 × 视角（品牌/渠道/店铺） | 每月 | 总览 KPI |
| `ad_spend` | 日 × 渠道 × 店铺 | 每日 | 广告/ROAS |
| `coverage_gate` | 月 × 数据槽 | 每日 | 覆盖率门控 |

**物化方式**：PostgreSQL 物化视图 + 增量刷新（`REFRESH MATERIALIZED VIEW CONCURRENTLY`），
或物理表 + 触发器增量。桶本身带 `algo_version` 列，算法升级时按版本重算。

### 5.3 算法注册表（法则库）

每个算法是**声明式**的，含：公式、依赖的数据槽、输出的桶、缺失时的行为。

```yaml
# algorithms/gp.yaml
id: algo.gp
name: 毛利 GP
version: 3
formula: "rev - cogs"                     # 纯公式，不含数据源
unit: THB
permission: L3
depends_on_slots: [slot.revenue, slot.cogs]
writes_bucket: pnl_sku_month
missing_policy: skip                      # 数据槽缺失时跳过，不补 0
trace: true
```

```yaml
# algorithms/gmp.yaml
id: algo.gmp
name: 毛利率
version: 3
formula: "rev == 0 ? null : gp / rev"
depends_on_slots: [slot.revenue, slot.gp]
missing_policy: skip
```
  
> **算法与数据来源分离**（需求第 4 条核心）：
> 算法只写 `formula` 与 `depends_on_slots`。**数据来自哪里**由数据槽（§5.4）单独定义。
> 换数据源只改槽定义，算法不动；改算法只改公式，数据源不动。

### 5.4 数据槽（DataSlot）：数据来源的唯一登记处

```yaml
# slots/slot.cogs.yaml
id: slot.cogs
description: 单件成本
source_kind: master_table               # master_table | api | upload | derived
source_ref: cost_master.v2               # 指向具体来源
key_strategy: barcode_then_sku           # 匹配键策略
coverage_gate: 0.80                      # 覆盖率低于此值视为不可用
freshness: 7d
permission: L4
```

**每个槽都有可用性状态**：`AVAILABLE / PARTIAL / MISSING`。
覆盖率低于 `coverage_gate` → `MISSING` → 依赖它的算法 `skip`（显示"待接入"，绝不补 0）。

### 5.5 值输出保证（需求第 4 条："保证每个值都能基于现有数据输出计算结果"）

运行时对每个字段执行如下判定，**结果写入 `AlgoTrace`**：

```
for field in contract.columns:
    algo = registry[field.algo_id]
    slots = [s for s in algo.depends_on_slots]
    if all(slots available and coverage >= gate):
        value = execute(algo.formula, data)         # 计算出值
        trace = {field, algo_id, slots, skipped: false}
    else:
        value = null                                 # 不补 0、不估算、不摊分
        trace = {field, algo_id, slots, skipped: true, reason: "slot.X MISSING"}
```

**三条铁律**（承袭 KODP 的 fail-closed 纪律）：

1. **缺失必跳过**：数据槽不可用 → 该值置 `null` + 前端显示 `待接入`／`—`。
2. **禁止伪值**：不得用 `0`、均值、比例分摊、演示数据填补。
3. **可追溯**：每个非空值都能沿 `AlgoTrace` 回溯到「哪条法则 + 哪些真实数据」。

### 5.6 规则引擎（Rule Engine）

运算法则（口径/费率/阈值）从代码里抽出来，落成**可版本化的规则集**：

```yaml
# rules/platform_fee.tk.yaml
id: rule.tk.fee
version: 6
scope: {platform: TK, country: TH}
items:
  - id: payment_gateway
    rate: 0.03
  - id: platform_commission
    rate: 0.10
    effective_from: 2026-07-01
  - id: commerce_growth_fee
    rate: 0.075
    vat_included: true
    effective_from: 2026-05-01
  - id: platform_infrastructure
    flat_per_order: 1          # THB
  - id: live_special_commission
    rate: 0.0428
  - id: pick_pack
    flat_per_order: 12         # THB
```

**规则集是唯一事实源**：改费率只改这一处，全域生效，且带 `version` 便于审计追溯。

### 5.7 增量与失效

| 事件 | 动作 |
|---|---|
| 新数据落地 | 标记受影响桶为 `stale` |
| 算法升级（`algo_version` 变更） | 只重算该算法写入的桶 |
| 规则变更（`rule_version` 变更） | 重算依赖该规则的桶 |
| 用户请求命中 `stale` 桶 | 返回旧值 + `precomputed:false` 标记，后台异步刷新（**不阻塞**） |

## 6. 核心设计三：IT 集成控制面（MCP / API 授权与状态）

需求第 5 条的落地。**IT 后台必须能直接管理所有 MCP 与 API 的授权与状态，以及账号启用状态。**

### 6.1 控制面全景

```
IT 控制台 (M-ADMIN)
├── 集成清单 (Integrations)
│   ├── MCP Servers        ← 注册 / 授权 / 探活 / 启用停用 / 配额
│   ├── API Connectors     ← OAuth / 密钥 / 有效期 / 限流 / 状态

└── 健康与审计 (Health & Audit)
    ├── 探针结果 / 配额消耗 / 失败告警
    └── 全部操作 append-only 留痕
```

### 6.2 集成实体模型

| 表 | 关键字段 | 说明 |
|---|---|---|
| `int_mcp_server` | `id, name, transport, endpoint, auth_ref, status, last_probe_at, quota` | MCP 服务器注册 |
| `int_api_connector` | `id, platform, oauth_client_ref, secret_ref, scopes, expires_at, status, rate_limit` | API 连接器（**密钥只存引用，不落明文**） |

| `int_grant` | `id, entity_id, granted_to, scope, granted_at, expires_at, revoked_at` | 授权记录（时间盒） |

### 6.3 状态机（所有集成实体统一）

```
        注册
         │
         ▼
    ┌─────────┐  授权成功   ┌───────────┐  停用   ┌──────────┐
    │ PENDING ├───────────►│  ACTIVE   ├────────►│ DISABLED │
    └────┬────┘            └─────┬─────┘         └────┬─────┘
         │ 授权失败              │ 探活失败/过期        │ 启用
         ▼                       ▼                    │
    ┌─────────┐            ┌───────────┐              │
    │  ERROR  │◄───────────┤  DEGRADED │◄─────────────┘
    └─────────┘            └───────────┘
```

**统一约束**：
1. `ACTIVE` 只是**必要条件**：KODP 的经验是「库里状态是 ACTIVE，但签名无效 = 无效」，
   所以任何集成的可用性 = **状态位 AND 凭证有效性 AND 探活通过**。
2. **密钥永不落库明文**：只存 `*_ref`，指向密钥库（KODP §6.5 同款 KEK 加密思路）。
3. **IT 只见元数据**：IT 可管理授权与状态，但**默认看不到任何业务数值**（承袭 KODP P3 铁律）。

### 6.4 IT 控制台交互（关键页面）

| 页面 | 能力 | 默认状态 |
|---|---|---|
| 集成总览 | 所有 MCP/API 的状态灯 + 最近探活 + 配额余量 | 卡片式，一目了然 |
| MCP 服务器 | 新增/编辑/信任/停用/删除、查看工具清单 | 列表 |
| API 连接器 | OAuth 发起/刷新、密钥轮换、Scope 编辑、限流配置 | 列表 + 抽屉详情 |
| 账号启用 | 服务账号启用/停用、绑定关系、配额分配 | 表格（默认展开状态列） |
| 探活与告警 | 手动探活、历史曲线、失败告警订阅 | 图表 |
| 审计 | 全部控制面操作流水，不可删改、可导出 | 表格 |

> **与 KODP 经验对接**：KODP 踩过「机器人不在目标群导致发送失败」「BC 有但无 advertiser 账号」
> 这类**授权存在但实际不可用**的坑。控制面必须**区分「授权状态」与「可用性」**，
> 并在 UI 上明确展示「已授权但探活失败」这类中间态（上图的 `DEGRADED`）。

## 7. 核心设计四：策略实验室（自迭代自优化算法 + 选型式决策）

需求第 6 条的落地。

### 7.1 定位

给用户一块**专门区域**，用于：
1. 查看算法模型的**当前参数与表现**；
2. 通过**选型方式**（不是填表）做决策与策略调整；
3. 系统据用户选择**自迭代优化**，并把结果反馈回预计算层。

### 7.2 自迭代闭环

```
    ┌──────────────────────────────────────────────────────┐
    │  1. 观测 (Observe)                                    │
    │     算法表现：命中率 / 覆盖度 / 用户采纳率 / 预测偏差    │
    └───────────────────────┬──────────────────────────────┘
                            ▼
    ┌──────────────────────────────────────────────────────┐
    │  2. 生成候选 (Propose)                                │
    │     基于历史数据自动生成 N 个参数方案（选型卡）          │
    └───────────────────────┬──────────────────────────────┘
                            ▼
    ┌──────────────────────────────────────────────────────┐
    │  3. 用户决策 (Decide)  ★选型式交互                     │
    │     展示 2–4 个方案，每个含：改动内容/预期影响/风险       │
    │     用户点选一个，或选「保持现状」                       │
    └───────────────────────┬──────────────────────────────┘
                            ▼
    ┌──────────────────────────────────────────────────────┐
    │  4. 应用 (Apply)                                      │
    │     更新规则集/算法参数 → 标记受影响预计算桶 stale       │
    └───────────────────────┬──────────────────────────────┘
                            ▼
    ┌──────────────────────────────────────────────────────┐
    │  5. 评估 (Evaluate) → 回到 1                          │
    │     A/B 对比新旧参数的实际表现，记录到策略历史           │
    └──────────────────────────────────────────────────────┘
```

### 7.3 选型式交互契约

**决策项一律以「选项」而非「输入框」呈现**（需求明确要求"以选型方式提供"）：

```ts
// contracts/strategy-choice.ts —— v1.0
export interface StrategyChoice {
  id: string;
  title: string;                          // 如"渠道费率口径"
  context: string;                        // 为什么要决策
  current: ChoiceOption;                  // 当前值
  options: ChoiceOption[];                // 2–4 个候选（含 current）
  impactPreview: ImpactPreview;           // 每个选项的预期影响
  blocking: boolean;                      // 是否阻塞其他功能
  decideBy?: string;                      // 建议决策截止
}

export interface ChoiceOption {
  key: string;
  label: string;
  description: string;
  expectedEffect: string;                 // 如"净利率 34.45% → 36.14%"
  risk: "low" | "medium" | "high";
  reversible: boolean;
  recommended?: boolean;
}
```

**用户侧只有三种动作**：`选 A` / `选 B`（…） / `保持现状`。绝不让人填公式。

### 7.4 内置的自迭代能力

| 能力 | 说明 |
|---|---|
| 参数调优 | 对费率、阈值、覆盖率门限等做网格/贝叶斯搜索，产出候选 |
| 口径对照 | 同一指标多口径并列（承袭 KODP 口径 A/B 的实测差异表经验） |
| 异常自检 | 数据分布漂移检测，超阈值时生成"是否调整"的选型卡 |
| 采纳学习 | 记录用户历次选择，优先推荐其偏好风格（保守/激进） |
| 回滚 | 任何策略变更可一键回滚到上一个稳定版本 |

### 7.5 策略历史（可追溯）

每次策略变更落一行：`策略 ID / 旧值 / 新值 / 决策人 / 时间 / 决策依据（当时的数据快照哈希） / 实际效果`。
这保证**任何数值变化都能解释**（KODP 的经验教训：口径变更不追溯会导致无法解释"为什么变了"）。

## 8. 核心设计五：插槽架构（预留其他功能模块接入）

需求第 7 条的落地。**从项目第一行代码就预留**。

### 8.1 模块清单（SlotManifest）

每个功能模块在注册中心声明自己：

```yaml
# slos/report.slot.yaml
id: module.report
name: 经营报表
version: 2.1.0
kind: page                       # page | panel | widget | background-job
entry: ./report/index.ts
nav:
  group: 经营分析
```

### 8.2 组合规则

| 规则 | 说明 |
|---|---|
| 声明式挂载 | 模块只声明「挂到哪个槽」，不写布局代码 |
| 能力协商 | 主机检查模块所需 `data_slots` / `permissions` 是否满足，不满足则降级或隐藏 |
| 独立升级 | 模块自带 `version` 与 `minHostVersion`，可独立发版 |
| 隔离 | 模块故障不拖垮主机（错误边界 + 超时） |
| 可停用 | IT 可在控制台停用任一模块，不影响其他模块 |

### 8.3 UI/UX 预留

| 预留 | 做法 |
|---|---|
| 导航 | 侧栏/顶栏由 manifest 动态生成，新增模块自动出现 |
| 布局 | 页面为命名网格槽（`main.content` / `main.side` / `header.actions` …） |
| 主题 | CSS 变量契约，模块不写死颜色 |
| 空态 | 模块未启用时槽位显示占位说明，而非报错 |
| 设置 | 每模块的 `settings_schema` 由主机统一渲染设置页 |

### 8.4 升级对接

```
新模块注册 → 能力协商 → 权限裁决 → 数据槽检查 → 挂载渲染
                                     │
                                     └─ 缺槽 → 降级渲染（显示"待接入"区块，不崩）
```

## 9. 核心设计六：报表与 P&L 的分层阅览

需求第 8、9 条的落地。

### 9.1 五层阅览层级（按信息概括程度）

```
L0 总览 (Overview)          ── 全局 KPI 卡，一屏看完
 │        点击任一卡片/板块
 ▼
L1 板块 (Domain)            ── Konvy官方 / Housebrand / Offline / GT / 其他
 │        点击板块
 ▼
L2 渠道 (Channel)           ── 平台-国别：TK-TH / SHOPEE-TH / LAZADA-TH …

 ▼
L3 店铺 (Store)             ── 单店：GMV / 订单 / 费用 / P&L
 │        点击店铺
 ▼
L4 SKU 明细 (SKU)           ── 单 SKU：销量 / 收入 / COGS / GP / 净利
```

| 层 | 信息概括度 | 默认展示内容 | 默认状态 |
|---|---|---|---|
| L0 | 最概括 | 全局 KPI（GMV / GP / 净利 / ROAS） | 常驻展开 |
| L1 | 高 | 板块卡片（金额 + 占比 + 环比） | **收起**，点击展开 |
| L2 | 中 | 渠道行（金额 + 费率 + 净额） | **收起** |
| L3 | 低 | 店铺行（明细指标） | **收起** |
| L4 | 最细 | SKU 行（全字段） | **收起**，虚拟滚动 |

### 9.2 P&L 与经营报表的模块区分

| 维度 | 经营报表 (`M-REPORT`) | P&L (`M-PNL`) |
|---|---|---|
| 视角 | 运营视角（量、额、动销） | 财务视角（收入、成本、利润） |
| 口径 | GMV 为主 | Net Revenue 为主（口径可切换） |
| 分层 | L0→L4 五层 | 收入→COGS→GP→费用→CM1→CM2→净贡献 |
| 口径切换 | 不需要 | **必须支持**（承袭 KODP 口径 A/B 经验） |

两者**共享 L0 总览**，但从 L1 开始分叉，各自独立演进。

### 9.3 层级跳转与展开（需求第 9 条）

| 交互 | 行为 |
|---|---|
| 点击 L1 板块卡片 | 跳转/展开到 L2 渠道层，URL 携带 `?level=channel&domain=housebrand` |
| 点击 L2 渠道行 | 展开 L3 店铺层（**行内展开**，不跳页） |
| 点击 L3 店铺行 | 抽屉展示 L4 SKU（**不离开当前页**） |
| 面包屑 | 始终显示当前层级路径，可逐级返回 |
| 深链 | 每一层状态可复制 URL，分享后直达 |

### 9.4 默认收起契约（硬性要求）

**所有可收起扩展的表格默认收起** —— 写进渲染层契约：

```ts
  L3: false,       // 店铺默认收起
```

| 保存 | 「保存为模板」→ 让用户**自命名** → 选档（个人/团队/系统，受权限约束） |
| 套用 | 从模板列表一键套用，重建整个 `QueryState` + 列偏好 + 布局 |
| 设默认 | 可将某模板设为「本页默认」，下次进入自动套用 |
| 分享 | 生成分享链接（团队/系统档） |
| 智能推荐 | 基于 `useCount` 与用户操作习惯，在模板中心顶部推荐 |

### 10.4 与 QueryState 的关系

模板**就是**一个被持久化的 `QueryState` + 视图偏好。这保证：
- 模板天然可深链（§9.3）；
- 新增筛选维度时模板自动兼容（协议版本号处理）。

## 11. 性能预算与毫秒级响应

需求第 11 条的落地。

### 11.1 性能预算（硬指标）

| 指标 | 目标 | 实测方式 |
|---|---|---|
| 首屏可交互 (TTI) | < 1000 ms | Lighthouse / 真实设备 |
| 筛选响应（命中预计算） | < 100 ms | 埋点 P95 |
| 筛选响应（未命中） | < 500 ms | 埋点 P95 |
| 滑块拖动实时反馈 | < 16 ms/帧 | WASM 本地即时算 |
| 层级展开 | < 50 ms | 已预取数据 |
| 大表格滚动 | 60 fps | 虚拟滚动 |

### 11.2 优化手段（分层）

| 层 | 手段 |
|---|---|
| **预计算**（最重要） | §5 的物化桶，把重算消灭在请求之前 |
| 查询 | 索引下推、分页下推、只查需要的列、物化视图并发刷新 |
| 缓存 | Redis 缓存 `ResultSet`（键 = `queryHash`）；CDN 缓存静态资源 |
| 传输 | gzip/brotli、增量补丁（只传变化部分）、GraphQL 式字段选择 |
| 前端 | 虚拟滚动、列级增量渲染、Web Worker 处理大数据、WASM 做即时运算 |
| 资源 | 首屏代码分割、路由级懒加载、字体子集化 |
| 渲染 | `requestIdleCallback` 做非关键渲染、避免布局抖动 |

### 11.3 缓存键与失效

```
cacheKey = hash(canonical(QueryState) + algoVersion + ruleVersion + dataVersion)
```

- **数据版本**变化 → 相关桶失效；
- **算法/规则版本**变化 → 依赖它们的键失效；
- 失效用 Redis 的 keyspace notification 广播，避免全量清空。

## 12. 数据模型（核心表）

### 12.1 事实表

| 表 | 粒度 | 关键字段 |
|---|---|---|

### 12.2 维表

| 表 | 说明 |
|---|---|
| `dim_brand` | 品牌 |
| `dim_channel` | 渠道（平台-国别） |
| `dim_store` | 店铺（带 `database + platform + shop_id` 唯一键） |
| `dim_product` | 产品主数据 |
| `dim_date` | 日历（含财年、周、季） |

### 12.3 预计算表

见 §5.2 的桶清单，每个桶是物理表 + `algo_version` + `refreshed_at`。

### 12.4 唯一键纪律（承袭 KODP 红线）

- **跨库/跨平台店铺合并唯一键 = `database + platform + shop_id / unique_key`**。
  不带库名会误并（KODP 实测存在同 `(platform, unique_key)` 但确为不同店的记录）。
- 总表行键 = `product_id`；SKU 只作精确辅助匹配。
- 未核对的重叠禁止跨库求和。

## 13. 权限模型（RBAC + ABAC）

| 项 | 设计 |
|---|---|
| 密级 | L1 公开 / L2 内部 / L3 敏感 / L4 核心 |
| 行级键 | `brand` / `channel` / `store` / `set_id` / `product_status` |
| 求值顺序 | DENY 优先，未显式授予即拒绝（fail-closed） |
| 管数分离 | IT 默认无业务数值读取权（可管授权与状态，不可看数） |
| 未知字段 | 不进 DOM、不进导出、不进 API 响应 |
| 脱敏 | L3/L4 降级用区间/分位/band 展示 |

## 17. 交接说明

- **契约优先**：`contracts/` 目录下的协议文件是层间唯一接口，改契约须升版本号。
- **单一事实源**：算法在 `algorithms/`、数据槽在 `slots/`、规则在 `rules/`，不在代码里散落。
- **闸门纪律**：所有数值必须有 `AlgoTrace`；所有可折叠表格默认收起；所有缺失显示"待接入"。
- **文档同步**：改架构必改本文档；改口径必改 `06-计算公式与来源字典.md`。
