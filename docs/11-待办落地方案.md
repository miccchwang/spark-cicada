## F4 · 角色模板默认勾选组设计 【直接采用】

角色模板 = **开箱即用的预设起点**（不是权限来源）。管理员套用后可自由增删。

| 模板 | 模块 | 勾选组 | 维度 | 密级 | IT 业务数值 |
|---|---|---|---|---|---|
| `role.admin` | 全部 | 四组全选 | 全维度 | L4 | — （见备注） |
| `role.it` | 集成控制台 / 账号管理 / 用户分组 / 审批中心 | **无（禁止）** | 无 | L1 | ❌ 恒 false |
| `role.finance` | 报表 / P&L / 策略实验室 | `grp.cost_profit` + `grp.roi` | 全维度 | L4 | ✅ |
| `role.brand_mgr` | 报表 / P&L | `grp.ops` + `grp.cost_profit` | 本品牌 | L3 | ✅ |
| `role.channel_ops` | 报表 / P&L | `grp.ops` + `grp.inventory` | 本渠道 | L2–L3 | ✅ |
| `role.supply_chain` | 报表 | `grp.inventory` | 本仓/本品类 | L2 | ✅ |
| `role.base` | 报表（只读） | 无 | 无 | L1 | ❌ |

**默认规则**
1. 勾选组默认**整组勾选**；管理员可在组内取消个别字段。
2. 维度默认**限定到本责任范围**（本品牌/本渠道），不默认全量。
3. 密级默认取该角色**下限**，提级需显式操作。
4. `role.admin` 特殊：作为 T1 拥有全部模块与四组；但 **D7 仍适用** —— 若某 T1 账号同时承担 IT 职责，
   仍需区分"管理员身份"与"IT 身份"（建议**分设账号**）。
5. 模板变更 → 生成新版本，已套用账号**不自动跟随**（避免静默扩权），需管理员确认。

**交付**：模板预设表写入 `docs/07` §7；实现时落 `templates/role.*.yaml`。

## F8 · 抄送与会签策略 【直接采用】

**结论**：默认**知会**（不阻断），仅在高风险场景升级为**会签**。

| 模式 | 抄送人权限 | 是否阻断 |
|---|---|---|
| **知会**（默认） | 可见该申请，无决定权 | ❌ 不阻断（审批人 +1 决定即可） |
| **会签**（条件触发） | 有**否决权**（否决即驳回） | ✅ 阻断 |

**升级为会签的触发条件**（任一命中即会签）：

| 条件 | 说明 |
|---|---|
| 密级 = L4 | 核心数据变更 |
| 跨部门 | 跨部门授予（本就需 T1，会签 +1 的上级） |
| 有效期 > 90 天 | 长期授权 |
| 涉及 `grp.roi` 或 `grp.cost_profit` | 影响投资/利润口径的数据 |
| 被授范围包含 ≥ 10 个账号或分组 | 批量授权 |

**配置项**：
```yaml
cc_policy:
  default_mode: notify          # notify | cosign
  cosign_triggers:
    - level: L4
    - cross_dept: true
    - expiry_days_gt: 90
    - data_use_groups: [grp.roi, grp.cost_profit]
    - grant_scope_accounts_gte: 10
  empty_cc_behavior: notify     # +2 不存在时：notify 或 skip
```

**落地**：`contracts/permission-request.ts` 的 `CcRecord.vetoed` 已在三轮预留；
审批状态机增加 `COSIGN_PENDING`（待会签）。

### F8 落地收口（2026-10-06 补）

会签的**接收侧**（否决阻断 `req.Approve`）此前已实现，但**发送侧**留有五个缺口，
且都不报错、只是静默不生效：

| # | 缺口 | 后果 |
|---|---|---|
| 1 | `RouteInput.ExpiryDays` 生产路径**从不填充** | 「有效期 > 90 天 ⇒ 会签」真实提交时**永远不成立** |
| 2 | `RouteInput.BatchSize` 生产路径**从不填充** | 「批量授予 ≥ 10 ⇒ 会签」真实提交时**永远不成立** |
| 3 | `+2` 缺失降级时未跳过 `approver` 本人 | 降级目标 = 审批人自己，抄送形同虚设 |
| 4 | 虚线汇报未与 `+2`/审批人去重 | 同一人重复入名单，待办计数虚增 |
| 5 | `empty_cc_behavior` 配置项**未实现** | 契约里写了 `notify/skip`，服务端忽略 |

**已落地**：

1. **`req.expiryDaysFrom(r)`**：由 `RequestedExpiry - CreatedAt` 推导天数，
   **向上取整**（23 小时算 1 天）—— 向下取整会让「90 天零几小时」漏掉会签；
   无有效期/已过期 ⇒ 0，不凭空升级为会签。
2. **`req.grantedAccountScope(d)`**：由维度的被授范围基数求和估规模；
   `includeDescendants=true` 时按 2 倍保守**高估** ——
   宁可多触发一次会签，不可漏一次（批量风险来自覆盖面）。
3. **`chain.CosignTrigger(in, ccp)`**：会签触发判定单列成纯函数，
   返回 `(是否触发, 原因)`。原因进 `CcRecord.Reason`，供审计复盘
   「这单为什么曾被判高风险」。
4. **`chain.SetCosignMode(recs, account, cosign, reason)`**：
   就地覆盖指定抄送人的模式，**绝不增删名单**；已是 cosign 时**不降级**
   （会签是唯一阻断高风险授予的机制），且降级不改 `Reason`（不抹掉触发依据）。
5. **`chain.EmptyCcBehavior`**：`notify`（默认，降级为 `+1` 的直属上级）/
   `skip`（无可抄送人则不留记录）。
6. **来源单一**：`Validation.CCs` 与 `Validation.Route` 出自**同一次** `Org.Route`
   —— `Route` 内含 `time.Now()`，两次调用会让「审批人来自一次路由、
   抄送来自另一次」，且 `NotifiedAt` 不一致。
7. **漂移自证**：`Validate` 末尾自检「名单里有 cosign 但未命中任一触发条件」⇒
   直接报错。会签被**误标**的后果是申请永远卡在 `COSIGN_PENDING`，
   而表象只是「审批很久没动」，极难定位。

**闸门**：`gate/f8_cosign_sendside_test.go`（新增 7 组，gate 包 `--- PASS` 59→85）。

> ★ **本闸门的核心教训（值得全仓复用）**：
> 原有的 `TestG7_CosignTrigger` 测的是 **`RouteInput` 入参**，不是**链路**。
> 它自己 `new` 出 `ExpiryDays: 91`，而没人保证生产路径会填这个字段 ——
> 于是两条触发条件在生产上恒不成立，闸门却一直全绿。
> **判据**：`grep` 断言依赖的核心字段，看生产路径里**有没有真实赋值点**；
> 只有测试在构造、生产从不填的值 = 恒真 = 没有断言。
> 本文件补的正是「从 `Submit` 进、从状态出」的链路级断言。

**实测注入破坏（5 处，全部被准确拦下）**：

| 注入 | 被哪条断言拦下 |
|---|---|
| 链路不填 `ExpiryDays`（回退到修复前） | `TestG7_CosignByExpiry_ThroughSubmitPath` |
| 链路不填 `BatchSize` | `TestG7_CosignByBatch_ThroughSubmitPath` |
| 天数向下取整 | `TestG7_CosignByExpiry_ThroughSubmitPath`（90天零1小时边界） |
| `+2` 缺失时降级给审批人本人 | `TestG7_EmptyCcBehavior` |
| Route 私自标 cosign（与会签判定漂移） | 漂移自证「会签标记与触发条件不一致」 |

## F9 · 矩阵型组织链路解析 【✅ 已拍板：A 单主属】

**背景**：一人可能属多部门（主属 + 兼属）、且有实线/虚线两套汇报。这会同时影响**数据链**与**审批链**。

| 方案 | 做法 | 结论 |
|---|---|---|
| **A 单主属** ✅ | 每人只有一个**主属部门**与**唯一实线上级**；兼属/虚线仅作"借调标记"，不参与审批 | **用户选定** |
| B 多主属 + 最近原则 | 允许多个归属；审批人取"与申请数据链同部门的上级" | 未采用 |
| C 显式指定 | 每条数据链显式指定审批人 | 未采用 |

**最终口径（A）**：
1. 每人有且仅有一个 `primaryDept` 与一个**实线上级**（`supervisor`）。
2. 兼属/虚线汇报记入 `dottedLineSupervisors[]`，**仅用于抄送**，不参与审批路由。
3. 兼属场景的额外权限走**时间盒临时授权**，到期自动回收。
4. 数据链责任人**必须落在唯一部门**（避免跨部门判定歧义）。

**落地要点**：
- `OrgNode` 增加 `primaryDept` 与 `dottedLineSupervisors[]`。
- 数据链责任人取 `primaryDept` 主管。
- 兼属期间权限 = 临时授权（时间盒）。

## F10 · 数据链责任人维护方式 【✅ 已拍板：C 混合】

| 方案 | 做法 | 结论 |
|---|---|---|
| A 从组织架构同步 | 责任人 = 部门主管（由 `dim_org` 派生） | 部分采用（作为默认层） |
| B 静态配置 | 手工指定责任人 | 部分采用（作为覆盖层） |
| **C 混合** ✅ | **默认从组织派生**（A），**支持对个别渠道/店铺手工覆盖**（B） | **用户选定** |

**最终口径（C）**：
1. **默认**：数据链责任人 = 该数据所属 `primaryDept` 的主管（**自动派生**）。
2. **覆盖**：允许对个别渠道/店铺**手工指定**责任人，覆盖项标注"由 X 于 Y 手工设定"。
3. **冲突**：**手工覆盖优先于派生**。
4. **失效**：手工项的责任人若**离职/停用** → 自动失效并**回退到派生**。

## F11 · 是否需 RPO = 0 【✅ 已拍板：C 分级】

**现状**：**地域内**异步 ⇒ RPO > 0（同地域延迟低，实际丢失窗口为**秒级**）。

| 方案 | 做法 | 结论 |
|---|---|---|
| A 保持异步 | 全部异步 | 未采用 |
| B 同步复制 | 全部同步 | 未采用 |
| **C 分级** ✅ | **业务数据异步**；**审计/权限/密钥元数据同步** | **用户选定** |

**最终口径（C）**：
1. **业务数据**（事实表/桶/维表）→ **异步**（T+1 批处理可容忍，主库无额外延迟）。
2. **不可丢元数据**（审计表 / 权限表 / 密钥元数据）→ **同步复制**（RPO = 0）。
3. 两类走**独立复制通道**，互不影响；同步通道故障时**告警并阻断相关写操作**（fail-closed）。
4. 因已改为**每地域独立主备**，不存在跨洋同步，同步复制代价可控。

## F12 · 备份归档格式与字段范围 【✅ 直接采用】

```
backup/
  2026-09/                        # 数据月份
    manifest.json                 # 清单：表名、行数、时间范围、sha256、生成时间、所属地域
    dim/                          # 维表（小，全量）
      dim_brand.parquet
      dim_channel.parquet
      dim_store.parquet
      dim_product.parquet
      dim_org.parquet
    fact/                         # 事实表（按日分区）
      fact_channel_sales/
        dt=2026-09-01/part-0.parquet
        ...
    buckets/                      # 预计算桶快照
      pnl_month.parquet
    README.txt                    # 解密与加载指引（不含密钥）
```

| 项 | 决策 |
|---|---|
| 主格式 | **Parquet**（列式、压缩率高、分析友好） |
| 辅格式 | 同时提供 **CSV（UTF-8 BOM）** 一份，便于 Excel 直接打开 |
| 分区 | 事实表按 `dt=YYYY-MM-DD` 分区 |
| 校验 | `manifest.json` 内含各文件 `sha256` + 总清单校验 |
| 加密 | 归档整体加密（受 KEK 保护）；`README.txt` 说明如何用密钥解密 |
| 禁止 | **归档内不得含任何密钥、凭据、明文密码**（闸门 G12 校验） |
| 时间范围 | 仅**上一个月**的完整数据；不含跨月补录 |

## F13 · 地域内切换自动化程度与脑裂防护 【✅ 已拍板：B 半自动】

> 因已改为**每地域独立主备**（§B1），切换是**地域内**行为，不涉及跨洋。

| 方案 | 做法 | 结论 |
|---|---|---|
| A 全手动 | T1 执行脚本，逐步确认 | 未采用 |
| **B 半自动** ✅ | 系统**自动检测主故障 + 告警**，执行需 **T1 一键确认** | **用户选定** |
| C 全自动 | 满足条件自动提升备 | 未采用 |

**最终口径（B）**：
1. 监控自动检测本地域主库故障 → 立即告警（钉钉 CRITICAL）。
2. 系统给出**提升指引**，**T1 一键确认**后执行提升。
3. 全流程留痕（谁、何时、哪地域、切换原因）。

**脑裂防护**（强制，与本项绑定）：

| 防护 | 做法 |
|---|---|
| **禁止双写** | 备库**只读**（PostgreSQL `hot_standby = on`，只读副本） |
| **禁止跨地域写同一行** | 两地域业务分区，各行只归一个地域 |
| **见证者仲裁** | 引入轻量"见证者"（Redis/etcd 小实例，**放第三可用区**），提升需见证者同意 |
| **Fencing** | 提升前**强制隔离旧主**（撤销其网络/凭据），防止旧主继续写入 |
| **切换窗口** | 记录切换时间点，恢复后**先对账再反向同步** |
| **人工兜底** | 任何自动检测都必须经 T1 确认才执行提升 |

### G12 落地收口（2026-10-06 补）

> **背景（第五个变种，同一个病）**：G12 四条断言所依赖的判定函数
> `CheckMonthlyQuota` / `CheckNoCrossRegionWrite` / `CheckFailoverFencing` /
> `CheckRollbackKeepsAudit`，此前**全仓没有任何非测试调用点** ——
> 唯一「调用」它们的就是它们自己的测试。于是：
>
> | 没有的链路 | 于是恒真的断言 |
> |---|---|
> | 没有下载路径 | 「同月第二次下载被拒」 |
> | 没有跨地域写路径 | 「禁止跨地域写同一行」 |
> | 没有切换路径 | 「切换必先 fencing」 |
> | 没有回滚路径 | 「回滚不动审计」 |
>
> 四条**永远为真**的断言，而 `docs/05` 标着「✅ 已实现」。
> **判据同上**：`grep` 断言依赖的核心函数，看生产路径里有没有真实调用点。

**落地（`internal/dr`，纯 Go、不依赖数据库）**：

1. **`DownloadService.RequestDownload`**（§6.4 / B3）：分地域 + 分账号 + 按自然月；
   配额 1 次/月；拒绝路径**不消耗配额**；拒绝也留痕（谁/何时/哪月/哪地域/校验和）；
   签名 URL 出站前过 `CheckNoCredentialsInURL`（docs/09）。
   **双防线**：`CheckMonthlyQuota` 判因（人类可读）+ `Store.ConsumeOnce` 原子兜底
   （并发下只有一个能过 —— check-then-act 会把「每月 1 次」变成 2 次）。
2. **`RowWriter.Upsert` / `GuardRowWrite`**（§6.1.1）：跨地域写被拒，且
   **下游存储根本不会被调用**（拒绝发生在到达存储之前）。
3. **`Promote` / `Fence` / `FencingFrom`**（§6.6 / F13=B）：
   ★ **fencing 三项从站点真实状态推导，不接受调用方声明**。
   若 fencing 由调用方传布尔值，闸门测的就还是入参 —— 生产路径「声明 true」
   即可绕过真正的隔离动作（这正是 F8 轮的教训）。故 `Promote` **不接收** Fencing 参数，
   而是 `FencingFrom(cluster, witness, lsn)` 现场推导：跳过 `Fence()` ⇒ 必拒，
   且拒绝时**集群纹丝不动**（不得出现「旧主已降级、备库未提升」的中间态）。
4. **半自动纪律**：`EvaluateProbe` 只产出「建议切换」告警，**绝不自动切、绝不自动切回**；
   切换须 T1 显式 `Promote`，且旧主降级后写通道**保持隔离**。
5. **`PlanRollback` / `VerifyRollbackAudit`**（§6.3 / B2）：180 天窗 / 仅 T1 /
   二次确认 / 回滚前先快照 / **审计表永不回滚**；回滚后审计行数减少即报错。

**闸门**：`gate/g12_dr_chain_test.go`（7 组链路断言，gate 包 `--- PASS` 118→125）；
`dr/dr_test.go`（17 条）。

**实测注入破坏（7 处，全部被准确拦下）**：

| 注入 | 被哪条断言拦下 |
|---|---|
| 摘掉配额闸门（不再调 `CheckMonthlyQuota`） | `TestG12_DownloadQuotaChain`（拒绝须携带闸门文案） |

> **背景（第七个变种，同一个病）**：`gate.CheckPerf` 是 G8 四条阈值的判定函数，
> 但它**全仓没有任何非测试调用点** —— 唯一「调用」它的就是它自己的 `_test.go`；
> `.github/workflows/ci.yml` 里也**没有** docs/05 尾注所说的 `gate-perf` 作业。
> 于是「首屏 TTI < 1000ms」「筛选 P95 < 100/500ms」「首屏产物 gzip < 200KB」
> **四条一条都没在把关**，而 docs/05 标着「✅ 已实现」。
>
> **判据同上**（复用前六轮的方法论）：`grep` 断言依赖的判定函数，
> 看生产路径里有没有真实调用点；只存在于测试 ⇒ 恒真 ⇒ 没有断言。

**落地**：

1. **`backend/internal/perf`** —— 判定执行侧：
   - `Report.Measured` 显式声明**哪些指标真的被测过**；
   - `Judge` 只采信已测项：未测字段**即便填了值也不采信**
     （否则「填个 0 就通过」会让闸门再次形同虚设），且未测项被**如实列出**；
   - 未测用**负哨兵**喂给 `CheckPerf`（预算被强制为正 ⇒ 哨兵永不误判为超标）；
   - `strict` ⇒ 任一未测即判失败（「没测」不等于「通过」）；
   - 已测项为负、预算非正、未知指标名 ⇒ **一律报错**（不许静默）。
2. **`backend/cmd/spark-perf`** —— 执行入口（退出码 0/1/2）。
   ★ 这是 `gate.CheckPerf` 的**真实生产调用点**。
   `--measure-bundle <dir>` 真实测量首屏产物 gzip：只计 `.js/.css/.html`、
   **排除 `.map`**、逐文件 gzip 后求和（真实 HTTP 是每个文件各自压缩下发的）。
3. **CI `perf` 作业**：构建前端 → `spark-perf --measure-bundle ../web/dist`，
   并并入汇总作业 `gate` 的 `needs`。
4. **接线闸门 `gate/g8_perf_wiring_test.go`**（本轮的「闸门」）：
   - ① CI 必须有 `perf` 作业、且**真的调用** `spark-perf`、且进了汇总 `needs`；
     否则「判定器存在但没人跑」=「不存在」；
   - ② docs/05 的四条阈值必须**逐字等于** `gate.DefaultPerfBudget()`（阈值只许一处真值）；
   - 两条都配**负向自测**（残缺 workflow / 篡改阈值 ⇒ 必须报错）。

**实测注入破坏（全部被准确拦下）**：

| 注入 | 结果 |
|---|---|
| 首屏产物换成 400KB 不可压缩 payload | `✗ 首屏产物 gzip 超标：实测 400055B > 预算 204800B`，退出码 1 |
| `--in` 报告 TTI = 5000ms | `✗ 首屏 TTI 超标：实测 5000ms > 预算 1000ms`，退出码 1 |
| 报告里塞巨大值但**不声明为已测** | **不产生违规**（未测不采信），且被列入未测项 |
| 指标名拼错（`bundle_size`） | 报错 + 退出码 2（不许静默变成「什么都没测」） |
| CI 去掉 `perf` 作业 / 摘掉 `gate.needs` 里的 perf | 接线闸门失败 |
| docs/05 阈值改成 9999ms | 阈值漂移闸门失败 |

**仍未覆盖（诚实标注）**：`TTI` / `筛选 P95` 需要无头浏览器 / 真库才能产出
**有意义**的数字（在内存假 Store 上测「筛选 P95 < 100ms」会永远通过 —— 那是假闸门）。
故这两项当前标记为**未测**，非严格模式不判失败但打进日志；接上测量源后改 `--strict` 即可。
