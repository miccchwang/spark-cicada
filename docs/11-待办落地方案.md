## F4 · 角色模板默认勾选组设计 【直接采用】

角色模板 = **开箱即用的预设起点**（不是权限来源）。管理员套用后可自由增删。

| 模板 | 模块 | 勾选组 | 维度 | 密级 | IT 业务数值 |
|---|---|---|---|---|---|
| `role.admin` | 全部 | 四组全选 | 全维度 | L4 | — （见备注） |
| `role.it` | 集成控制台 / 账号管理 / 用户分组 / 审批中心 | **无（禁止）** | 无 | L1 | ❌ 恒 false |
| `role.finance` | 报表 / P&L / 策略实验室 | `grp.cost_profit` + `grp.roi` | 全维度 | L4 | ✅ |
| `role.brand_mgr` | 报表 / P&L | `grp.ops` + `grp.cost_profit` | 本品牌 | L3 | ✅ |
| `role.channel_ops` | 报表 / P&L | `grp.ops` + `grp.inventory` | 本渠道 | L2–L3 | ✅ |
| `role.supply_chain` | 报表 | `grp.inventory` | 本仓/本品类 | L2 | ✅ |
| `role.base` | 报表（只读） | 无 | 无 | L1 | ❌ |

**默认规则**
1. 勾选组默认**整组勾选**；管理员可在组内取消个别字段。
2. 维度默认**限定到本责任范围**（本品牌/本渠道），不默认全量。
3. 密级默认取该角色**下限**，提级需显式操作。
4. `role.admin` 特殊：作为 T1 拥有全部模块与四组；但 **D7 仍适用** —— 若某 T1 账号同时承担 IT 职责，
   仍需区分"管理员身份"与"IT 身份"（建议**分设账号**）。
5. 模板变更 → 生成新版本，已套用账号**不自动跟随**（避免静默扩权），需管理员确认。

**交付**：模板预设表写入 `docs/07` §7；实现时落 `templates/role.*.yaml`。

## F8 · 抄送与会签策略 【直接采用】

**结论**：默认**知会**（不阻断），仅在高风险场景升级为**会签**。

| 模式 | 抄送人权限 | 是否阻断 |
|---|---|---|
| **知会**（默认） | 可见该申请，无决定权 | ❌ 不阻断（审批人 +1 决定即可） |
| **会签**（条件触发） | 有**否决权**（否决即驳回） | ✅ 阻断 |

**升级为会签的触发条件**（任一命中即会签）：

| 条件 | 说明 |
|---|---|
| 密级 = L4 | 核心数据变更 |
| 跨部门 | 跨部门授予（本就需 T1，会签 +1 的上级） |
| 有效期 > 90 天 | 长期授权 |
| 涉及 `grp.roi` 或 `grp.cost_profit` | 影响投资/利润口径的数据 |
| 被授范围包含 ≥ 10 个账号或分组 | 批量授权 |

**配置项**：
```yaml
cc_policy:
  default_mode: notify          # notify | cosign
  cosign_triggers:
    - level: L4
    - cross_dept: true
    - expiry_days_gt: 90
    - data_use_groups: [grp.roi, grp.cost_profit]
    - grant_scope_accounts_gte: 10
  empty_cc_behavior: notify     # +2 不存在时：notify 或 skip
```

**落地**：`contracts/permission-request.ts` 的 `CcRecord.vetoed` 已在三轮预留；
审批状态机增加 `COSIGN_PENDING`（待会签）。

## F9 · 矩阵型组织链路解析 【✅ 已拍板：A 单主属】

**背景**：一人可能属多部门（主属 + 兼属）、且有实线/虚线两套汇报。这会同时影响**数据链**与**审批链**。

| 方案 | 做法 | 结论 |
|---|---|---|
| **A 单主属** ✅ | 每人只有一个**主属部门**与**唯一实线上级**；兼属/虚线仅作"借调标记"，不参与审批 | **用户选定** |
| B 多主属 + 最近原则 | 允许多个归属；审批人取"与申请数据链同部门的上级" | 未采用 |
| C 显式指定 | 每条数据链显式指定审批人 | 未采用 |

**最终口径（A）**：
1. 每人有且仅有一个 `primaryDept` 与一个**实线上级**（`supervisor`）。
2. 兼属/虚线汇报记入 `dottedLineSupervisors[]`，**仅用于抄送**，不参与审批路由。
3. 兼属场景的额外权限走**时间盒临时授权**，到期自动回收。
4. 数据链责任人**必须落在唯一部门**（避免跨部门判定歧义）。

**落地要点**：
- `OrgNode` 增加 `primaryDept` 与 `dottedLineSupervisors[]`。
- 数据链责任人取 `primaryDept` 主管。
- 兼属期间权限 = 临时授权（时间盒）。

## F10 · 数据链责任人维护方式 【✅ 已拍板：C 混合】

| 方案 | 做法 | 结论 |
|---|---|---|
| A 从组织架构同步 | 责任人 = 部门主管（由 `dim_org` 派生） | 部分采用（作为默认层） |
| B 静态配置 | 手工指定责任人 | 部分采用（作为覆盖层） |
| **C 混合** ✅ | **默认从组织派生**（A），**支持对个别渠道/店铺手工覆盖**（B） | **用户选定** |

**最终口径（C）**：
1. **默认**：数据链责任人 = 该数据所属 `primaryDept` 的主管（**自动派生**）。
2. **覆盖**：允许对个别渠道/店铺**手工指定**责任人，覆盖项标注"由 X 于 Y 手工设定"。
3. **冲突**：**手工覆盖优先于派生**。
4. **失效**：手工项的责任人若**离职/停用** → 自动失效并**回退到派生**。
5. 全部变更落审计。

## F11 · 是否需 RPO = 0 【✅ 已拍板：C 分级】

**现状**：**地域内**异步 ⇒ RPO > 0（同地域延迟低，实际丢失窗口为**秒级**）。

| 方案 | 做法 | 结论 |
|---|---|---|
| A 保持异步 | 全部异步 | 未采用 |
| B 同步复制 | 全部同步 | 未采用 |
| **C 分级** ✅ | **业务数据异步**；**审计/权限/密钥元数据同步** | **用户选定** |

**最终口径（C）**：
1. **业务数据**（事实表/桶/维表）→ **异步**（T+1 批处理可容忍，主库无额外延迟）。
2. **不可丢元数据**（审计表 / 权限表 / 密钥元数据）→ **同步复制**（RPO = 0）。
3. 两类走**独立复制通道**，互不影响；同步通道故障时**告警并阻断相关写操作**（fail-closed）。
4. 因已改为**每地域独立主备**，不存在跨洋同步，同步复制代价可控。

## F12 · 备份归档格式与字段范围 【✅ 直接采用】

```
backup/
  2026-09/                        # 数据月份
    manifest.json                 # 清单：表名、行数、时间范围、sha256、生成时间、所属地域
    dim/                          # 维表（小，全量）
      dim_brand.parquet
      dim_channel.parquet
      dim_store.parquet
      dim_product.parquet
      dim_org.parquet
    fact/                         # 事实表（按日分区）
      fact_channel_sales/
        dt=2026-09-01/part-0.parquet
        ...
    buckets/                      # 预计算桶快照
      pnl_month.parquet
    README.txt                    # 解密与加载指引（不含密钥）
```

| 项 | 决策 |
|---|---|
| 主格式 | **Parquet**（列式、压缩率高、分析友好） |
| 辅格式 | 同时提供 **CSV（UTF-8 BOM）** 一份，便于 Excel 直接打开 |
| 分区 | 事实表按 `dt=YYYY-MM-DD` 分区 |
| 校验 | `manifest.json` 内含各文件 `sha256` + 总清单校验 |
| 加密 | 归档整体加密（受 KEK 保护）；`README.txt` 说明如何用密钥解密 |
| 禁止 | **归档内不得含任何密钥、凭据、明文密码**（闸门 G12 校验） |
| 时间范围 | 仅**上一个月**的完整数据；不含跨月补录 |

## F13 · 地域内切换自动化程度与脑裂防护 【✅ 已拍板：B 半自动】

> 因已改为**每地域独立主备**（§B1），切换是**地域内**行为，不涉及跨洋。

| 方案 | 做法 | 结论 |
|---|---|---|
| A 全手动 | T1 执行脚本，逐步确认 | 未采用 |
| **B 半自动** ✅ | 系统**自动检测主故障 + 告警**，执行需 **T1 一键确认** | **用户选定** |
| C 全自动 | 满足条件自动提升备 | 未采用 |

**最终口径（B）**：
1. 监控自动检测本地域主库故障 → 立即告警（钉钉 CRITICAL）。
2. 系统给出**提升指引**，**T1 一键确认**后执行提升。
3. 全流程留痕（谁、何时、哪地域、切换原因）。

**脑裂防护**（强制，与本项绑定）：

| 防护 | 做法 |
|---|---|
| **禁止双写** | 备库**只读**（PostgreSQL `hot_standby = on`，只读副本） |
| **禁止跨地域写同一行** | 两地域业务分区，各行只归一个地域 |
| **见证者仲裁** | 引入轻量"见证者"（Redis/etcd 小实例，**放第三可用区**），提升需见证者同意 |
| **Fencing** | 提升前**强制隔离旧主**（撤销其网络/凭据），防止旧主继续写入 |
| **切换窗口** | 记录切换时间点，恢复后**先对账再反向同步** |
| **人工兜底** | 任何自动检测都必须经 T1 确认才执行提升 |
