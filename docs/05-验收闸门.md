# 05 · 验收闸门（CI Gates）

> 承袭 KODP 的「闸门」思想：把架构约束变成**可自动失败的断言**，防止设计随时间腐化。
> 版本 v1.2（2026-10-05 二轮修订：新增 G12 备份与容灾闸门；G7 补充权限细则）

---

## 1. 为什么需要闸门

KODP 的经验：**设计写在文档里会漂移，写在闸门里才不会**。
本项目的架构约束（三段式解耦、默认收起、缺失不补 0 等）全部固化为断言。

---

## 2. 闸门清单

### G1 · 分层依赖闸门

| 断言 | 说明 |
|---|---|
| `M-FILTER` 不含网络调用 | 静态分析：无 `fetch` / `axios` / `http` 引用 |
| `M-RENDER` 不读 `QueryState` | 静态分析：渲染模块无 `QueryState` 导入 |
| `M-QUERY` 不含业务公式 | 静态分析：无 `gp` / `cogs` / `gmp` 字面公式 |
| 无反向依赖 | L5 不直接依赖 L2 及以下 |

### G2 · 默认收起闸门

| 断言 | 说明 |
|---|---|
| 所有可折叠表格初始 `open=false` | 渲染快照断言（L0 总览除外） |
| `DEFAULT_EXPANDED` 契约值一致 | 单元测试 |

### G3 · 缺失值闸门

| 断言 | 说明 |
|---|---|
| 任何非空值有 `AlgoTrace` 且 `skipped=false` | 契约校验 |
| `skipped=true` 的字段值必为 `null` | 契约校验 |
| 页面不出现用于占位的 `0` | 渲染断言（真实计算为 0 除外，需白名单） |
| 缺失显示文案为 `待接入` / `—` | 渲染断言 |

### G4 · 算法/数据槽分离闸门

| 断言 | 说明 |
|---|---|
| 算法 YAML 中无数据源字段 | schema 校验：`formula` 不含 `source` / `table` |
| 每个 `depends_on_slots` 已注册 | 引用完整性 |
| 每个槽有 `coverage_gate` | schema 校验 |

### G5 · 覆盖率门控闸门

| 断言 | 说明 |
|---|---|
| 覆盖率 < 门限 → 依赖算法 `skip` | 注入低覆盖数据，断言跳过 |
| 不补 0、不摊分 | 断言输出为 `null` |

### G6 · 预计算一致性闸门

| 断言 | 说明 |
|---|---|
| 桶 `algo_version` == 注册表版本 | 启动检查 |
| 桶数据与源数据对平 | 抽样重算对比 |
| 算法升级后仅重算受影响桶 | 变更后断言 |

### G7 · 权限闸门

| 断言 | 说明 |
|---|---|
| 无权字段不进 DOM | 渲染断言 |
| 无权字段不进导出 | 导出断言 |
| 无权字段不进 API 响应 | 接口断言 |
| IT 账号无法读业务数值 | 端到端断言 |
| **IT 的「业务数值」勾选项置灰不可点** | UI 断言（D7=取消） |
| **代授不溢出**：下级权限 ⊆ 上级权限 | 注入越权代授，断言被拒（D13） |
| **代授不溢出（链路级）** | 上述断言此前只测 `DelegationAllowed` 的**返回值**，而该函数在服务端**唯一**的调用点就是这条断言本身 —— 没有任何代码会真的构造一次代授，于是「代授不溢出」在实现侧**恒真**。现补 `authz.Resolver.Delegate` 真实路径 + 链路断言（`gate/g7_delegation_chain_test.go`）：从代授入口进，以「落库的 `GrantRecord` + 求值出的 `source.fromDelegations`」出 |
| **代授上界取「求值结果」而非「原始声明」** | 授出者原始声明里有 `m.secret` 但被 DENY ⇒ 代授 `m.secret` 仍须被拒；组依赖未满足的组、已过时间盒的来源，同样不得作为上界下授。反向断言：`delegateAll` 的留痕实际范围必须等于**求值结果**（不是「声明什么记什么」） |
| **代授溢出即拒且不产出结果** | 溢出时返回 `nil` 结果（有结果就会被调用方落库）；拒绝码 `DELEGATION_OVERFLOW`；不得给自己代授（`SAME_ACCOUNT`）；上界取不到时 **fail-closed** |
| **代授来源可溯源且不串桶** | 合法代授落库后 `source.fromDelegations` 含 `delegate:<授出者>`，且**不得**混入 `fromApprovedRequests`（两个桶的追责路径完全不同） |
| **分组 DENY 优先** | 分组授权与个人勾选冲突时取 DENY（D12） |
| **申请未批不通** | 未走完审批的 Entitlement 不生效（D14） |
| **获批即开通** | `APPROVED` 的申请必须**真的**把权限落到账号 Entitlement（`req.Activate`）；反向断言：DRAFT/SUBMITTED/APPROVING/COSIGN_PENDING/REJECTED/WITHDRAWN/BLOCKED_CROSS_DEPT 七态逐一注入，断言被拒**且目标授权纹丝不动** |
| **开通幂等** | 同一申请单重复生效不叠加模块/维度/勾选组、不重复记来源 |
| **开通不翻 DENY** | 申请里带某模块，但该模块已被管理员显式禁用 → 仍不可见（DENY 优先） |
| **来源可溯源** | 生效后 `EntitlementView.source.fromApprovedRequests` 含 `request:<审批人>@<申请单ID>`；代授不得混入该桶 |
| **+1 审批 / +2 抄送** | 提交后仅 +1 进审批队列；+2 或 +1 的直属上级进抄送列表 |
| **跨部门不可自助申请** | 跨部门数据项在自助申请页置灰；提交状态置 `BLOCKED_CROSS_DEPT` |
| **跨部门须 T1 批准** | 注入"非 T1 批准跨部门授予"，断言被拒 |
| **IT 不可勾选任一业务数据组** | 断言 `grp.ops`/`grp.cost_profit`/`grp.inventory`/`grp.roi` 对 IT 均不可选 |
| **勾选组依赖校验** | 勾 `grp.roi` 而缺 `grp.cost_profit`+`grp.inventory` 时提示/降级 |
| **会签触发** | 注入 L4 / 跨部门 / 有效期>90天 / 含 `grp.roi`·`grp.cost_profit` / 批量≥10 的申请，断言状态置 `COSIGN_PENDING` |
| **会签触发（链路级）** | 上述五项**不得只测 `RouteInput` 入参** —— 必须从 `req.Service.Submit` 入口进、以申请单状态出。历史缺陷：`ExpiryDays`/`BatchSize` 在生产路径上从未被填充（恒 0），导致「有效期>90天」「批量≥10」两条在真实提交时**永远不成立**，而闸门因直接构造入参而长期全绿。见 `gate/f8_cosign_sendside_test.go` |
| **会签名单与状态同源** | `Status=COSIGN_PENDING` ⇒ `CCs` 中必须**确有** cosign 记录；反向：低风险单**不得**残留任何 cosign 记录（否则永远无法通过审批） |
| **抄送名单无本人/无审批人/无重复** | 申请人本人、审批人（`+2` 降级不得落到 approver 自身）、虚线汇报与 `+2` 重复项，均不得出现在抄送名单 |
| **empty_cc_behavior** | `notify`：`+2` 缺失时降级为 `+1` 的直属上级（**不得**是审批人本人）；`skip`：无抄送记录 |
| **ccs jsonb 键名** | `fact_permission_request.ccs` 的键名须含 `cc/reason/mode/notifiedAt/vetoed/decidedAt`；`decidedAt` 未表态时**显式 null**（不得 omitempty），否则 0006 的 `v_cosign_pending` 取键恒 NULL |
| **会签否决生效** | 会签人否决后，申请必须为 `REJECTED`，权限不生效 |
| **知会不阻断** | 默认模式下抄送人未阅知，不阻断 +1 审批通过 |

## 3. 闸门执行

```bash
make gate          # 全部闸门
make gate-fast     # 静态闸门（G1/G4/G5）
make gate-auth     # 权限闸门（G2/G3/G7/G10）
make gate-precomp  # 预计算一致性（G5/G6）
make gate-dr       # 备份与容灾（G12）
make gate-compute  # 计算内核自检
make gate-sql      # SQL 迁移静态闸门（append-only / D7 / 可空 / region / 无凭据 / 种子诚实）
make gate-admin    # 控制面（G4 解耦 / G5 传播 / G6 局部重算 / G9 挂载 / G10 审计）
make gate-db       # 真库集成（需 SPARK_TEST_DB_DSN）
make gate-web      # 前端三闸门（G1 三段解耦 / G2 默认收起 / G3 缺失不填零）
make gate-secret   # 密钥扫描（G11，依赖 gitleaks）
make launch-check  # ★ 上线前证据链（见 §3.2）
```

任一闸门失败 → **阻断合并**（承袭 KODP 的「两个浏览器闸门转阻断」经验）。

### 3.1 ★ 跳过 ≠ 通过（闸门的第一纪律）

真库断言在**没有数据库**时会 `t.Skip`。如果 CI 也静默跳过，这些断言就
**从未被执行过**，而 CI 依然全绿 —— 这是**假绿**，比红灯危险得多。

因此：

| 环境 | `SPARK_TEST_DB_DSN` | `SPARK_REQUIRE_DB` | 行为 |
|---|---|---|---|
| 本地开发 | 未设 | 未设 | **跳过**（不阻塞日常开发），并在输出中明示「本轮未验证」 |
| CI | 已设（service 容器） | `1` | **必须真跑** |
| 误配 | 未设 | `1` | **直接失败**（拒绝以「跳过」冒充通过） |

对应实现：`backend/internal/store/integration_test.go: openTestDB`。

### 「同一个配置，多处消费」的一致性闸门

上面那张表只覆盖了**一处**消费端。真实事故发生在**多处消费端之间**：
迁移器读 `SPARK_DB_DSN`、集成测试读 `SPARK_TEST_DB_DSN`，而 CI 只设了后者
⇒ 真库迁移步骤以「未配置连接信息」秒退，其后所有真库闸门被连环 skip。
**两侧单看都自洽**，静态读任何单个文件都发现不了。

因此新增 `internal/gate/config_consistency_test.go`，把契约钉在一起：

| 断言 | 拦住的失效 |
|---|---|
| CI workflow 以 **YAML 键**注入 `SPARK_DB_DSN` 与 `SPARK_TEST_DB_DSN` | 只设一个名字 ⇒ 另一半静默失效/skip |
| CI workflow 设 `SPARK_REQUIRE_DB` | 真库段被 skip 却仍显示绿灯 |
| `db.DSNFromEnv()` 同时识别两个名字 | CI 设了但解析器不认 |
| `launch-check.sh` 显式 `env -u` 抹掉 DSN 做无库冒烟 | 上游注入 DSN ⇒ `healthz db=false` 断言因环境串味而失败 |
| `backend/README.md` 写明两个名字 | 运维照文档漏配 |

★ 该闸门首版是 `strings.Contains(yml, "SPARK_DB_DSN")` —— **弱断言**：
`SPARK_TEST_DB_DSN` 本身包含 `SPARK_DB_DSN` 子串，即使主名键被整行删掉
断言仍通过。**负向测试当场抓住**（注入违规后闸门没响），已改为断言 YAML 键形态
（`hasYAMLKey`）。教训：文本闸门必须贴着「真正产生效果的语法形态」写。

同理，前端闸门脚本曾因路径含空格崩溃却返回退出码 0（闸门静默放行），
现已修正，并对每项闸门做**负向测试**（注入违规必须 `exit 1`）。
**一条从不失败的闸门等于没有闸门** —— 新增闸门时必须同时提供负向用例。

### 3.2 上线前证据链（`make launch-check`）

`tools/verify/launch-check.sh` 把「能否上线」变成**一条命令、退出码可信**的结论：

| 段 | 断言 |
|---|---|
| 0 | 工具链就位（go / node / cargo） |
| 1 | `go build` + `go vet` |
| 2 | 迁移集校验（有库走 dry-run；无库走文件层 + SQL 静态闸门） |
| 3 | `go test ./...`（G1–G12 + 控制面 + SQL 静态） |
| 4 | **真库集成**（同上 + **M-COLLECT 临时仓库**：页级原子提交 / 断点续传 / 幂等 / 守卫过闸） |
| 4b | **真库数据面端到端**：迁移 → sparkd 带 DSN → `healthz db=true` → `/api/query` 真读库 |
| 5 | Rust `cargo test` + 内核 `--selftest` |
| 6 | 前端分层闸门 + 测试 + `tsc` + 构建 |
| 7 | **前端产物密钥扫描**（G11b） |
| 8 | **sparkd 真进程冒烟**：静态托管 / SPA fallback / `healthz` / 无库 500 / 未注册桶拒绝 |

第 8 段是**真起进程、真发 HTTP**，不靠 mock —— 它验证的是「交付物能被跑起来」，
而不只是「函数返回值正确」。这段曾抓出两个真实缺口：
sparkd 缺静态托管（前端产物是死文件）、冒烟缺 compute 内核（fail-closed 拒绝启动）。

第 4b 段与第 4 段的区别在于**它验证的是「接库真的生效」**，而不只是「SQL 语义正确」：
迁移跑过 ≠ 服务读得到库。该段曾抓出 sparkd `SPARK_MIGRATIONS_DIR` 相对路径按 cwd
解析、路径错就**静默降级**（只打一行 warn）—— 现已由 `/healthz.dbDegradeReason`
把「未配 DSN」与「配了但坏了」显式区分开。

#### 跨平台可移植性（★ 真实事故）

`launch-check` 曾连续三轮在 CI 上红，且**一条自定义 annotation 都没出现** ——
因为脚本死在最前面，而汇总段的 annotation 还没来得及输出。加了 EXIT trap
（`_on_exit` 打印「最后进入的步骤」）之后，才定位到：

```
[failure] launch-check 中途退出（exit 1），最后进入的步骤：0. 工具链
```

根因是**跨平台路径污染**：脚本原先无条件注入 Windows 专属工具链路径

```bash
export GOROOT="${GOROOT:-C:/Users/.../go1.27.1}"   # ← 无条件
```

本机无恙（托管的 `go.exe` 就在那儿）。但 CI 是 Linux：`GOEXE` 已正确按 PATH
回退成 `/usr/bin/go`，`GOROOT` 却仍被强制指到一个 **Windows 路径** ⇒ Go 找不到
自己的标准库 ⇒ `go version` 失败 ⇒ 步骤 0 判「go 不可用」⇒ 当场退出。
**报错信息把真正原因（路径污染）完全掩盖了。**

修法是加守卫：只有当 `GOEXE` 仍是托管绝对路径时，才注入其配套环境变量。

由此确立两条通用纪律：

1. **「注入安装路径派生的环境变量」必须先判断自己是否真在用那个安装。**
   否则「本机绿、CI 红」或反之，且报错方向会被彻底带偏。
2. **`A && B` 不可作段落的最后一条命令**：
   `[ "$FAIL" -gt 0 ] && { echo ...; exit 1; }` 在 `FAIL=0` 时整条语句返回 1，
   非零状态向下传染，配合 trap 就表现为「在步骤 0 中途退出」。
   一律改显式 `if`。这是 shell 里最经典也最隐蔽的退出码陷阱。

**闸门也要被闸门守卫**：新增
`TestConfig_LaunchCheckGuardsWindowsToolchain`（`config_consistency_test.go`），
用**区间断言**（而非全文 `Contains`）钉死「四个 export 必须落在守卫体内」，
并校验 `MANAGED_GO` 与 `GOEXE` 默认值同路径以防漂移。两种注入均已验证 FAIL。

> 若只写 `strings.Contains(sh, "export GOROOT")`，那么把 `export` 从守卫里
> **挪到外面**（等于把 bug 改回来）闸门依然全绿。当一条闸门决定「别的闸门是否
> 生效」时，它必须被独立、更严格的断言守住。

本地真库演练与 CI 的**环境必须逐项对齐**：本地演练曾因库名用 `spark` 而 CI 的
`POSTGRES_DB` 是 `spark_cicada`，导致真库段全线失败 —— 看起来像代码 bug，
实为演练脚本没复现 CI「由 `POSTGRES_DB` 自动建库」这一步。
**环境差异被误判成代码缺陷，是本地演练最常见的陷阱。**

### 3.3 ★ M-COLLECT 临时仓库（staging）闸门

采集层是**唯一直接面对第三方平台**的地方：配额、限流、鉴权、分页全在这里踩坑。
它的失效模式有一个共同特征 —— **纯逻辑单测测不出来**。因此这一层的闸门分两类：
SQL/配置静态闸门（`go test` 即可跑），与**真库集成闸门**（必须有 DSN）。

#### 静态闸门（`sql_lint_test.go`）

| 断言 | 拦住的失效 |
|---|---|
| `staging_record` 有 `UNIQUE (job_id, idem_key)` 唯一索引 | 幂等去重退回应用层 ⇒ 竞态窗口下重复落库 |
| `collect_job` 有 `cursor / pages_done / rows_staged / gear_index / ok_streak` | 状态没落库 ⇒ 重启后整月重放 |
| `collect_rate_gear` 存在且种子覆盖 500ms…120000ms | 档位表缺失/端点漂移 |
| `staging_record.guard_state` 的 **DEFAULT 为 `'PENDING'`** | 默认放行（安全漏洞） |
| 各表有 `region` 列 | 分地域数据归属缺失 |
| 无硬编码密钥 | 凭据入库（G11） |

#### 跨文件一致性闸门（`config_consistency_test.go`）

档位表在**两处**定义：迁移种子（`0005`）与 `collect.GearTable`。
两边都「各自自洽」，静态读单个文件发现不了漂移 —— 因此新增
`TestConfig_GearTableMatchesCollectCode`，逐档比对 `index / delay_ms / label / recover_after`，
并断言端点恰为 500ms 与 120000ms。**两个方向都做了负向验证**（改任一单边均 FAIL）。

#### 真库集成闸门（`collectstore/integration_test.go`）

标 `Integration`，走与 §3.1 相同的 `SPARK_REQUIRE_DB` 纪律：本地无 DSN 跳过，
CI 无 DSN **直接失败**。共 8 条，全部对真 Postgres 跑：

| 断言 | 验证的行为 |
|---|---|
| `CommitPagePersistsDataAndCursorAtomically` | 数据行与游标同事务提交 |
| `ResumeFromCursorWithoutDuplicateCalls` | 断点续传 → 上游调用次数不增 |
| `UniqueIndexRejectsDuplicateIdemKey` | 重复页被 DB 层幂等拦下 |
| `GuardBlocksIncompleteFromProjection` | 不完整数据**进不了**投影层 |
| `GuardPassesAndReleaseCleansStaging` | 过闸后 staging 行被清理 |
| `GearTableMatchesHardcoded` | 库内档位表 == Go 常量 |
| `EmptyNaturalKeyRejected` | 空自然键被拒（防幂等键退化） |
| `SuiteIsNotSilentlySkipped` | 该套件不会被静默跳过 |

#### ★ 为什么这层非真库不可（两个生产级事故，纯单测全绿）

1. **`invalid byte sequence for encoding "UTF8": 0x00`（SQLSTATE 22021）**
   幂等键首版用 `"\x00"`（NUL）作分隔符。Go 字符串**允许** NUL，
   所以所有纯逻辑单测都通过；但 **PostgreSQL 的 `text` 存不了 NUL**，真库当场报错。
   改为 `"\x1f"`（U+001F）—— 同样不可打印（避免拼接歧义），但能存进 `text`。
   补了 `TestIdemKey_ContainsNoNULByte` 防复发（反向验证过确实会红）。

2. **`null value in column "reasons" ... violates not-null constraint`（SQLSTATE 23502）**
   `staging_ingest_guard.reasons` 是 `text[] NOT NULL DEFAULT '{}'`。
   **`DEFAULT` 只在列被「省略」时生效**；显式传 `nil []string`（pgx 会写成 SQL NULL）
   会覆盖 DEFAULT ⇒ 撞 NOT NULL。更阴的是它**只在成功路径触发**
   （失败时 `reasons` 非空），所以失败用例全绿、成功用例才炸。
   第一版只在 `Store.EvaluateGuard` 里把 nil 转成 `[]string{}` ——
   结果被**自己新写的 `TestEvaluate_PassedVerdictReasonsIsNonNil` 抓住**：
   那只是治标。正确修法是让 `collect.Evaluate` 自己就以 `reasons := []string{}` 起步，
   所有调用方自动安全。

> 教训：**「不能确认完整」不等于「完整」**。守卫必须 fail-closed；
> 同理，「纯单测绿」不等于「能落库」。凡是与**真实存储引擎语义**相关的约束
> （编码、NULL 语义、类型严格性），必须有真库闸门兜底。

#### 闸门自身的弱断言（★ 又一次同型事故）

`TestSQL_StagingGuardBlocksByDefault` 首版用
`strings.Contains(body, "'PENDING'")` 断言守卫默认值 —— **它永远为真**：
`guard_state` 的 CHECK 约束本身就写成 `IN ('PENDING','PASSED','REJECTED')`，
子串必然命中，与 DEFAULT 是什么**完全无关**。
负向测试（把 DEFAULT 改成 `'PASSED'`）**闸门没响**，暴露了这是条假闸门。

修法：新增 `defaultClauseFor(body, col)` —— 真正解析出该列的 `DEFAULT` 子句字面量
（剥掉列定义前导 `(`、按顶层逗号切分、以列名为首词匹配、
`DEFAULT` 字面量在 `" \t\n,)"` 处终止），再断言其为 `'PENDING'`。
并为本解析器补 `TestDefaultClauseFor` **自测**（7 个用例，含前导 `(` 的输入）。

> **一个「不报错但给出错误答案」的解析器，比一个直接崩溃的解析器更危险**
> —— 前者会让闸门永远绿灯。解析型闸门必须自带自测用例。

## 4. 新增闸门的纪律

新增架构约束时：
1. 先在 `docs/01` 写明约束；
2. 再在本文档加一条闸门；
3. 最后实现断言。

**顺序不可颠倒** —— 先有约束定义，才有断言。
