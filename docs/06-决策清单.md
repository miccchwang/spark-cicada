## D1 落地口径（多云多区）

用户原话：**「阿里云及aws，区域新加坡与美国」**。据此：

| 项 | 决策 |
|---|---|
| 云厂商 | **阿里云 + AWS 双云** |
| 区域 | **新加坡（ap-southeast-1 / AWS ap-southeast-1）** + **美国（AWS us-east-1 等）** |
| 部署形态 | Docker Compose（D5），双云各自起一套 |
| 数据同步 | 主库走内网/VPN（D9）；跨云通过加密通道，不直接暴露公网 |
| 选型理由 | 新加坡贴近泰国业务时区；美国区用于容灾/对美业务；双云避免单厂商锁定 |

## D4 落地口径（混合语言）

用户原话：**「go做业务编排，rust做核心计算与高性能模块」**。据此修订 `docs/01` §4：

| 层 / 模块 | 语言 | 判据 |
|---|---|---|
| 业务编排（`M-QUERY` 编排、`M-ADMIN`、`M-SLOT`、`M-AUTH`、`M-AUDIT`、`M-COLLECT`） | **Go** | 高并发、单二进制部署、生态成熟；**只编排、不重算** |
| 核心计算（`M-ALGO` 法则执行、`M-PRECOMP` 预计算、`M-RULE` 规则求值） | **Rust** | 批量数值运算、无 GC 抖动、类型强、可编译 WASM 复用前端 |
| 高性能模块（滑块实时重算、大结果集聚合、覆盖率校验） | **Rust（+ WASM）** | 毫秒级与 60fps 要求 |
| 前端交互 | **TypeScript + Solid** | — |

**边界纪律**：Go **不写数值公式**（公式一律在 Rust 算法内核）；Rust **不碰 HTTP 编排/鉴权**。
两者通过 gRPC/FFI 边界通信，契约见 `contracts/`。

## D7（第二轮修订）：IT 业务数值权限 —— **取消**

用户第二轮原话：**「it业务数值权限取消」**。

**最终口径**：**IT 不获得业务数值权限**，回到「管数分离」原则。

| 项 | 最终落地 |
|---|---|
| IT 可管理 | MCP/API 授权与状态、账号启用、用户分组、权限申请审批（**元数据层**） |
| IT 不可见 | **任何业务数值**（GMV / 成本 / 售价 / 毛利 / 净利…） |
| 字段级 | IT 对业务字段一律不可见（L1–L4 全不可见） |
| 实现 | `Entitlement.canViewBusinessValues` 对 IT 角色**恒为 false**，且**不可被勾选开启** |
| 审计 | IT 的全部控制面操作留痕；不含业务数值访问（因为不访问） |

> **意义**：这一条回到了 KODP 的安全红线 —— "系统被攻破"与"财务数据泄露"解耦。
> IT 拥有最大的系统权限，却看不到任何经营数字。

## D11（第二轮细化）：账号权限可勾选模块与数据维度

第一轮原话：**「不同帐号权限可勾选模块及数据纬度确定，不只是固定方案」**。
第二轮补强：**「角色模板为预设，允许管理员勾选权限」**。

**最终口径**：

| 项 | 决策 |
|---|---|
| 角色模板 | **预设**（起点），不是权限的唯一来源 |
| 勾选者 | **管理员**可勾选权限（赋予/调整账号的模块、维度、密级） |
| 勾选客体 | 模块 / 数据维度（行级）/ 字段密级（列级）/ 逐字段覆写 |
| 求值 | 模板起点 ⊕ 逐项勾选 ⊖ DENY(优先) ⊕ 临时授权，再受**职权向下覆盖**约束（D13） |
| 自助 | 用户还可在系统中**勾选数据权限后发起申请**（D14），审批通过即开通 |

**落地**：`contracts/entitlement.ts` + `docs/07-账号权限勾选设计.md`；
分组维度见 `docs/08`。

## D12–D14（第二轮新增）：分组 / 职权覆盖 / 权限申请

用户第二轮原话：**「新增用户分组功能，可建立群组与管理成员，审批及管理职责为用户职权向下覆盖，
申请权限可在系统中勾选数据权限后发起申请，审批通过即开通该申请帐户的数据权限」**。

| # | 决策 | 落地 |
|:--:|---|---|
| D12 | **用户分组**：可建立群组并管理成员 | 分组作为授权载体（组级授权，成员继承）；见 `docs/08` |
| D13 | **审批与管理职责 = 用户职权向下覆盖** | 上级可审批/管理下级的权限；不可反向、不可平级；见 `docs/08` §3 |
| D14 | **权限申请流**：用户勾选数据权限 → 发起申请 → 审批通过即开通 | 申请单 = 一份 `Entitlement` 草案；审批通过后写入生效；见 `docs/08` §4 |

> 三条合起来构成完整的「自助 + 审批」权限闭环：**用户申请 → 上级审批 → 系统开通**，
> 且与 D11 的"管理员可勾选"并存（管理员可直接勾选授予，用户也可自助申请）。
